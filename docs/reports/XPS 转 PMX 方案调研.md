# 内嵌读取器、双层映骨、借道 mmd_tools：XPS 转 PMX 插件方案

我们建议把插件做成"内嵌 XPS 读取器 → 中间人形骨骼模型 → mmd_tools 数据契约 → PMX"的四层结构，而不是在 XPS Tools 与 mmd_tools 之间再叠一层脚本。英、日、中三个社区自 2016 年起收敛到同一条手工链路——XPS Tools 导入 Blender、按字典改成 MMD 日文骨名、补骨与腿 IK、用 mmd_tools "Convert Model" 导出、再到 PMXEditor 用 準標準ボーン追加プラグイン 等插件收尾——但**没有任何现有工具同时覆盖改名、补骨/IK、A 姿势、材质、表情、物理与校验七件事**，而且 **2024 年 Blender 4.0/4.1 的 API 变更让上游 XNALaraMesh、Cats 与旧版 mmd_tools 同时失效**，XPS 侧至今只剩个人维护的分支。XPS 格式本身很小：骨骼只有名字、int16 父索引与 float3 位置，版本差异只有"是否带切线"与"权重是否变长"两个布尔分支，自写读取器约几百行即可，还能保留导入器丢掉的 `uvLayerId`、渲染 flags、默认姿势与 `+`/`-`/`|` 可选项信息。骨骼侧推荐"VRM/Unity 55 骨内部规范 + MMD 日文名输出层"的双层模型，匹配走"精确 XPS 预设 → Cats 式归一化词表 → VRM/Godot 式拓扑搜索"三级，每级结果都落到逐槽可改的 UI；缺失骨按 そぼろ 插件的开源移植（nanoem `ssb.cc`）公式生成，IK 用 あにまさ式 ver.2.3 的实测值（足ＩＫ loop 40 / 单位角 2 rad，つま先ＩＫ loop 3 / 4 rad，膝 X 限制 −180°～−0.5°）。社区对 A 姿势角度没有共识（45°、37°、34° 与实测上臂 29.7°、前臂 40.3° 并存），对 XPS `spine lower` 归 上半身 还是 下半身 也有分歧，这两项都应做成用户参数而不是常数。导出建议依赖 mmd_tools ≥ 4.5（GPL-3.0-or-later，通过 `bl_ext.*.mmd_tools` 动态导入），同时保留其纯 Python `core/pmx` 写出器作兜底；目标 Blender 4.2 LTS 起，插件以 GPL-3.0-or-later 发布。文末单列 14 项待负责人拍板的决策与推荐选项。

## 社区链路十年未变：Blender 做前半、PMXEditor 做后半，"一键通用"仍是空白

英文社区的"正典"由 2016 年的几篇 DeviantArt 教程奠定。Tokami-Fuko 在 Blender 2.49b 时代就强调 "When you convert to pmd-format you must copy all bone names for correct work with motions data"（[Tokami-Fuko 2016](https://www.deviantart.com/tokami-fuko/art/Converting-XPS-to-MMD-with-bones-598167627)）；Riveda1972 的转换指南主张**保留 XPS 原骨架而不重绑**（"When you have a working skeleton yet, it's simply foolish to not use it and to rig the model again."），并把缩放、绑定、物理、表情全部留给 PMX Editor（[Riveda1972 guide v1.1](https://www.deviantart.com/riveda1972/art/MMD-XNALara-to-MMD-Model-conversion-guide-v1-1-653374127)）。2018 年 powroupi 的 mmd_tools wiki 把流程工具化为 20 步：骨架以 Individual Origins 放大 10 倍 → "Convert Model" → mmd_tools_helper 批量改名 → 控制台查看缺失骨 → "Correct MMD Root and Center bones" → 一键加 leg/foot IK → Display Panel → 导出 PMX → 在 PMD/PMX Editor 修材质与 sphere 贴图（[powroupi wiki 教程](https://github.com/powroupi/blender_mmd_tools/wiki/Tutorial:-How-to-convert-a-3D-character-model-to-MMD)）。Hogarth-MMD 2025 年的《Mmd Model Conversion Notes》仍是最完整的英文检查表：改骨名 → 补 "mother bone" → 加腿脚 IK（必须是 root 子级）→ 缩放到 MMD 身高 → Display Panel → 材质（diffuse 1.0、ambient 0.4、specular 0.2–0.3）→ 表情分组 → PMX error checker → 在 MMD 用 VMD 测试 → 最后才加物理（[Hogarth 2025](https://www.deviantart.com/hogarth-mmd/art/Mmd-Model-Conversion-Notes-1186227547)）。日文侧 2023 年的 cgbox 文章在 Blender 3.5 上走 XNALaraMesh → mmd_tools "Convert Model" → 导出，却完全不提骨名问题（[cgbox 2023](https://cgbox.jp/2023/04/23/blender-xps-import-export/)）；中文 2017 年的六集全攻略则把改名/合并、IK、表情、物理、材质全部放进 PE（[Bilibili BV1Dx411J7Gu](https://www.bilibili.com/video/BV1Dx411J7Gu/)）。这种分工不是偶然：XPS 文件只有 Blender 插件能读，而 準標準ボーン追加、曲面自動設定（物理）、SimpleDivideMorph（表情左右拆分）、PMX 状態検証 只存在于 PMXEditor 的插件生态（[tktk 2023 插件清单](https://tktk.hateblo.jp/entry/2023/10/05/145115)）。

直接转换器存在三代，但都有明显缺口。mariokart64n 2019 年的独立 GUI "Xnalara to MMD Converter"（v1.32，可执行名 pmxconv）在 v1.31 加入 "automatic Japanese naming when appropriate and IK insertion"，但页面不提表情与物理（[mariokart64n](https://www.deviantart.com/mariokart64n/art/Xnalara-to-MMD-Converter-789330400)），而且 "doesn't work if Xnalara model doesn't have the xps.xps file"（[Jargonfox 2022](https://www.deviantart.com/jargonfox/journal/Some-tips-for-MMD-PMXEditor-and-Blender-907027358)）。Hogarth-MMD 的 bones_renamer（2018-01 创建、2022-02 最后推送）与 mmd_tools_helper（2018-05 创建、2021-08 最后推送）提供含 XNALara 列的 20 套骨名映射、Armature Diagnostic 与一键 leg/foot IK，但代码仍是 2.7x API（[mmd_tools_helper](https://github.com/Hogarth-MMD/mmd_tools_helper)）。2025–2026 年中文 GitHub 出现第三代：uitcis/Convert-to-MMD（GPL-3.0，24 个预设含 `xna_lara`，面板顺序 "转换为A-Pose → 归正骨架位置 → 1.重命名为MMD → 2.补全缺失骨骼 → 3.添加MMD IK → 4.创建骨骼集合 → 5.使用mmdtools转换格式"）（[Convert-to-MMD](https://github.com/uitcis/Convert-to-MMD)）；killinux/xps_to_mmd 用"纯拓扑+几何方法，不依赖骨名"在 Inase 模型上 2 秒生成 188 骨，却**不处理 T/A 姿势、缩放、贴图、表情**，且只在 1 个模型上验证（[xps_to_mmd README](https://raw.githubusercontent.com/killinux/xps_to_mmd/main/README.md)）；Convert_to_MMD5 最全（物理、表情、ARKit），但锚定 Blender 3.6.15，验收口径是 "rotation errors ≤12°"（[Convert_to_MMD5](https://github.com/killinux/Convert_to_MMD5)）；SaraKale/Model-To-PMX 是不依赖 Blender 的纯 Python 转换器，**只读二进制 .xps**、按包围盒归一化到 20 单位、固定反射 `(x, y, z) → (x, y, -z)`、0 表情、无物理（[Model-To-PMX README](https://raw.githubusercontent.com/SaraKale/Model-To-PMX/main/README.md)）。没有一个工具同时处理改名、补骨/IK、A 姿势、材质、表情、物理与校验并被多模型验证——这正是本插件的空间。

2024 年是工具链断裂年。Blender 4.0 "Layers and bone groups have been removed … Bone collections have been added instead"，节点组接口改为 `NodeTree.interface`（[Blender 4.0 Python API](https://developer.blender.org/docs/release_notes/4.0/python_api/)）；4.1 又移除了 `use_auto_smooth` 与 `create_normals_split`（[Blender 4.1 Python API](https://developer.blender.org/docs/release_notes/4.1/python_api/)），于是 XPS Tools 与 PMX 导入在 4.0.1/4.1 上同时报错（[Blender Artists 2024](https://blenderartists.org/t/all-pmx-and-xps-give-these-errors-on-import-what-am-i-doing-wrong/1530271)）。上游 johnzero7/XNALaraMesh 自 2021-06-10 起无代码提交，**GitHub API 报告 `license: null`**（[GitHub API](https://api.github.com/repos/johnzero7/XNALaraMesh)）；两个活跃分支中，mayloglog 的 "XPS Import/Export" 以 GPL-3.0-or-later 上架 extensions.blender.org，但面向 Blender 5.0+（v2.1.0 才对应 4.4）且禁用了二进制 .xps 导出（[extensions.blender.org io-xnalara](https://extensions.blender.org/add-ons/io-xnalara)），Valerie-Bosco 的 XNALara-io-Tools 覆盖 3.6–5.2 但仓库无 LICENSE（[XNALara-io-Tools](https://github.com/Valerie-Bosco/XNALara-io-Tools)）。MMD 侧则已稳定：MMD Tools v4.5.14（2026-09-02）面向 "Blender 4.2 LTS and newer"，GPL-3.0-or-later，下载量 60 万+（[extensions.blender.org mmd-tools](https://extensions.blender.org/add-ons/mmd-tools/)）。官方 Cats 已被标为 "100% abandoned"（[Cats issue #710](https://github.com/absolute-quantum/cats-blender-plugin/issues/710)），而新一代中文转换器全部锚定 Blender 3.x——"在 Blender 4.2+/5.x 上可用的 XPS→PMX 一键插件"是真实空白。

实践者反复踩的坑可以归为三层。命名层：骨名不是 MMD 日文名则 VMD 不生效，XPS 导出常留下 "Null_##" 占位名（[Nintendraw 2016](https://www.deviantart.com/nintendraw/art/MMD-Tut-How-to-Rename-Anything-in-PMXe-and-MMD-642315757)）。拓扑/姿势层：缺 センター/グルーブ/足ＩＫ 等 XPS 根本没有的骨；"Most XPS models are in T pose and VMD motion in A pose"（[DanceXR 1.3.6 devlog](https://stormlab.itch.io/dancexr/devlog/439796/release-136)）；捩りボーン 的 軸制限 在格式互转时被重算成"指向原点"而损坏，手臂乱扭 "twist bones are usually the culprit"（[ブロマガ ar2013830](https://site.nicovideo.jp/ch/userblomaga_thanks/archive/ar2013830)；[nekofac 2023](https://nekofac.com/archives/1187/)）。材质层：mmd_tools 的 Convert Model 曾直接把 Blender alpha 复制进 `mmd_material.alpha`，alpha=0 的材质导出后不可见（[mmd_tools issue #143](https://github.com/powroupi/blender_mmd_tools/issues/143)）；日文/中文贴图名编码错误导致"白模"（[OZ-Sys 2024](https://www.deviantart.com/oz-sys/art/MMD-Missing-textures-or-seeing-a-white-model-1106349911)）。验收标准则很经验化：日本社区公认用「極楽浄土」测试，因为 "全身の関節を使った振り付けになっていて、モデルの不備を見つけやすい"（[うー電車 2020](https://twitter.com/mokusorizm/status/1333709399580282880)）；Hogarth 的测试段是 PMX error checker 零报错 → PMXE "Morphs check" 预览全部表情 → MMD 随机注册测眨眼 → 载入 VMD 跳舞（[Hogarth 2025](https://www.deviantart.com/hogarth-mmd/art/Mmd-Model-Conversion-Notes-1186227547)）。插件若内置"载入标准 VMD 并量化偏差"的校验器，就把社区的经验式验收变成了可重复的回归测试。

## 推荐架构：九个可单独重跑的阶段围绕一个"中间人形模型"

架构上的核心主张是：**所有阶段都读写一个与 XPS、MMD 都无关的中间人形模型**（内部 ID 用 VRM/Unity 的 55 骨人形集合，再加 MMD 控制骨槽位），每个阶段是一个幂等的 Operator，用户可在任意阶段停下来手修再继续。这与 VRM Add-on "名称预设评分 → 结构搜索回退"（[human_bone_mapper.py](https://github.com/saturday06/VRM-Addon-for-Blender/blob/main/src/io_scene_vrm/common/human_bone_mapper/human_bone_mapper.py)）、Convert-to-MMD 的"预设 JSON + 逐槽 prop_search + 分步按钮"（[Convert-to-MMD](https://github.com/uitcis/Convert-to-MMD)）和 MMD Tools Append 以 `pose_bone.mmd_bone.name_j` 为"严格名"的做法（[mmd.py](https://raw.githubusercontent.com/MMD-Blender/blender_mmd_tools_append/main/mmd_tools_append/converters/armatures/mmd.py)）是同一思路的综合。下表给出每个阶段的推荐做法、备选与关键规则；细节在后文各节展开。

| # | 阶段 | 推荐做法 | 备选 | 关键规则 / 参数（来源） |
|---|---|---|---|---|
| 1 | 读取 XPS | 内嵌无依赖读取器：读 4 字节 uint32 与 `323232` 比较决定有无头部；`hasTangentVersion = verMinor <= 12 and verMayor <= 2`（有头部）/ 恒 `True`（无头部 `.mesh`）；`hasVariableWeights = verMayor >= 3`；字符串为 .NET 风格 7-bit 变长前缀 + `utf-8-sig`；骨骼 = 名 / int16 父（−1 无父）/ float3；面索引 uint32；`.mesh.ascii` 与 `.pose` 走文本解析 | 依赖 mayloglog（GPL，5.0+）或 Valerie-Bosco（无 LICENSE）分支的 XPS Tools | 常量 `MAGIC_NUMBER=323232`、`SETTINGS_LEN=1080`、`STRLEN=275`；flags 3/4/5 = 法线通道 swizzle，7 = `hasBoneDirections`（无任何实现读取其数据）（[read_bin_xps.py](https://raw.githubusercontent.com/johnzero7/XNALaraMesh/master/read_bin_xps.py)；[XPS 11.8.9 发布说明](https://xnalara.forumotion.com/t327-xna-posing-studio-11-8-9-view-mode-edition-release-189)） |
| 2 | 建 Blender 场景 | 坐标 `(x, -z, y)`、面绕向 `[f0, f2, f1]`、UV `v' = 1 - v`、不缩放；每 XPS 网格一个对象一个材质；按骨索引建顶点组；Armature 修改器命名 `mmd_armature`；自定义法线用 `normals_split_custom_set_from_vertices`；骨尾用 `boneTailMiddle` 启发式 | 直接复用 XPS Tools 导入结果再"收编" | 根骨尾 `head + (0, -0.5, 0)`、默认尾 `(0,0,-0.1)`、`MIN_BONE_LENGHT = 0.005`、辅助骨正则 `\b(hip)?(twist\|ctr\|root\|adj)\d*\b`（[import_xnalara_model.py](https://github.com/johnzero7/XNALaraMesh/blob/master/import_xnalara_model.py)） |
| 3 | 骨骼识别/映射 | 三级：精确 XPS 预设 → Cats/VRM 式归一化词表 → 拓扑/几何搜索；输出 `{slot_id: bone_name}` + 置信度；逐槽 UI 确认 | 只做预设精确匹配（mmd_tools_helper/Convert-to-MMD 模式） | 见第三节 |
| 4 | 清理、缩放、静置姿态 | twist/adj 并入父骨、`unused*` 删除、权重 `clean(0.001) → limit_total(4) → normalize_all`；按身高归一化；T→A 用"每顶点 Σwᵢ(Pᵢ·Rᵢ⁻¹)"矩阵法烘进网格与形态键后 `pose.armature_apply` | Cats `PoseToRest` / przemir 复制网格法；固定 12.5 缩放 | 见第四节 |
| 5 | 补骨 / IK / 付与 / 轴 | 按 ssb 公式生成标准与准标准骨；足ＩＫ loop 40 / 2 rad，つま先ＩＫ loop 3 / 4 rad；付与经 `mmd_bone.additional_transform_*`；ローカル軸 X 指向子骨、Z 近前后轴；`bone_id` 按目标顺序写入 | 只补标准骨，准标准留给 PMXEditor 插件 | 见第三节 |
| 6 | 材质 | 只接 diffuse 到 `mmd_base_tex`；`rgAlpha` 组 → 透明、后排、关边线；默认 toon 皮肤 toon02 / 其他 toon01；非 diffuse 贴图名写入材质 comment | 把 lightmap 预乘进 diffuse（需选项） | 见第五节 |
| 7 | 表情 | 生成标准名占位 + 面部骨 ボーンモーフ 打包成 群モーフ + 可选部件 材質モーフ | 全部留给 PMXEditor | 见第五节 |
| 8 | 物理 | 默认只建身体 ボーン追従 碰撞体；发/裙链生成为可选预设 | 全部留给 PmxTailor / 曲面自動設定 | 见第五节 |
| 9 | 校验与导出 | 按 PMXE 10 类 49 项 + Nuthouse01 顺序自检；崩溃级错误阻断导出；`Model.create(...)` 收编后 `bpy.ops.mmd_tools.export_pmx` 或 `core.pmx.exporter.export(...)`；兜底直接构造 `pmx.Model` 写盘 | 完全自写 PMX 写出器 | 见第五、六节 |

mmd_tools 一侧的"最小导出契约"决定了阶段 2–8 的落点。一个可导出的模型 = 一个 `mmd_type == "ROOT"` 的 Empty → 其第一个 ARMATURE 子对象 → 骨架递归子对象中 `type == "MESH" and mmd_type == "NONE"` 的网格；`Model.create(name, name_e, scale, obj_name, armature_object=..., add_root_bone=False)` 一步建好 root 与骨架并创建付与亲功能依赖的 `mmd_shadow`/`mmd_dummy` 骨骼集合——在非 MMD 骨架上直接应用 Rotate+/Move+ 会因缺少这两个集合失败（[mmd_tools issue #340](https://github.com/MMD-Blender/blender_mmd_tools/issues/340)；[core/model.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/model.py)）。顶点组名必须等于 **Blender 骨名**而不是 `name_j`；每根 pose bone 填 `mmd_bone.name_j / name_e / bone_id`，导出顺序严格按 `bone_id` 升序（−1 排最后），`mmd_tools.fix_bone_order` 会按"父在子前、付与亲在被付与者前"重排并压实 ID（[properties/pose_bone.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/properties/pose_bone.py)；[core/pmx/exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。贴图通过**节点名**识别（`mmd_base_tex` / `mmd_sphere_tex` 的 `ShaderNodeTexImage`），toon 走 `is_shared_toon_texture + shared_toon_texture`（0–9 对应 toon01–toon10）或 `toon_texture` 路径；网格按对象名排序、同名材质跨网格合并为一个 PMX 材质；形态键第 0 个为 Basis，morph 顺序由 `表情` 表示枠内顺序决定；刚体/Joint 走 `FnRigidBody.new_*_object + setup_*_object`；`display_item_frames` 至少含 `Root` 与 `表情` 两个 special 枠；导出前模型须 `is_built=False`、骨架处于 REST（[core/pmx/exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)；[core/rigid_body.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/rigid_body.py)）。坐标上 mmd_tools 导出做 `pmx_matrix[1], pmx_matrix[2]` 行交换（Blender `(x, y, z)` → PMX `(x, z, y)`，不翻符号）并乘 `scale`（默认 12.5），UV `(u, 1 - v)`，所以 XPS 导入后面朝 Blender −Y 的模型无需再旋转即对应 MMD 的面朝 −Z（[operators/fileio.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/fileio.py)）。

从另一个扩展调用 mmd_tools 的现成范例是 MMD Tools Append 的 `import_mmd_tools()`：依次对 `"bl_ext.blender_org.mmd_tools"`、`"bl_ext.user_default.mmd_tools"`、`"bl_ext.vscode_development.mmd_tools"` 做 `importlib.import_module` 并缓存（[utilities.py](https://raw.githubusercontent.com/MMD-Blender/blender_mmd_tools_append/main/mmd_tools_append/utilities.py)）。版本门槛应读包内 `MMD_TOOLS_VERSION` 并要求 ≥ 4.5——当前 `bone_id` 与 `display_connection_*` 方案由 2025-04 的 PR #205 确立（[PR #205](https://github.com/MMD-Blender/blender_mmd_tools/pull/205)），而 4.5.6+ 又陆续新增 "Texture Relative Path"、"auto texture relative path depth"、材质排序等导出参数（[v4.5.14 release](https://github.com/MMD-Blender/blender_mmd_tools/releases/tag/v4.5.14)），调用 `pmx_exporter.export(**kwargs)` 时只应传本版本存在的参数。`core/pmx/__init__.py` 仅依赖 `logging, os, struct`，提供完整的 PMX 2.0 读写（默认 `utf-16-le`，`Header.updateIndexSizes` 自动选索引字节数），是"mmd_tools API 变化过大时直接构造 `pmx.Model` 写盘"的天然兜底（[core/pmx/exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。

## 骨骼：三级识别、双层映射、公式化补骨，每一步都可手修

### XPS 的"事实标准名"稳定到足以硬编码，分歧只在 `spine lower`

XPS 社区没有官方骨名规范——Riveda1972 直言 "XPS models don't actually have [a naming standard]"，但 Padme4000 列表派生的那套名字 "is common and diffused enough to be considered a kind of 'standard'"（[Riveda1972 bones reference list](https://www.deviantart.com/riveda1972/art/MMD-XPS-to-MMD-bones-reference-list-619693351)）。四条独立来源——Riveda 的参考表、Hogarth 的 `bones_dictionary.csv` `xna_lara` 列、Convert-to-MMD 的 `presets/xna_lara.json`、Cats 词表中 `Arm_\Left_Shoulder_1` 一类归一化条目——对约 60 根骨的解释几乎完全一致（[bones_dictionary.csv](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/mmd_tools_helper/bones_dictionary.csv)；[Cats armature_bones.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature_bones.py)），因此**插件应把它作为"XPS 预设"直接内置**：

| XPS 通用名 | MMD 日文名 | 备注 |
|---|---|---|
| `root ground` | `全ての親` | 导入器对 `root ground`/无父骨骼特殊处理，尾指 −Y |
| `root hips` | `センター` | 多数模型此骨无权重；若有权重需拆（见下） |
| `pelvis` | `下半身` | 变形骨 |
| `spine lower` / `spine lower b`（常缺）/ `spine upper` / `spine upper b`（常缺） | `上半身` / `上半身b` / `上半身2` / `上半身3` | Riveda 标注 b/3 "Many mmd models don't have them" |
| `head neck lower` / `head neck upper` | `首` / `頭` | |
| `head eyeball left/right` | `左目` / `右目` | |
| `arm left shoulder 1` / `shoulder 2` / `elbow` / `wrist` | `左肩` / `左腕` / `左ひじ` / `左手首` | 右侧同构 |
| `arm left finger 1a/1b/1c` | `左親指０/１/２` | `1a` 正好对应准标准 親指０ |
| `arm left finger 2a/2b/2c` … `5a/5b/5c` | `左人指１/２/３`、`左中指…`、`左薬指…`、`左小指…` | 全角数字 |
| `leg left thigh` / `knee` / `ankle` / `toes` | `左足` / `左ひざ` / `左足首` / `左つま先` | |
| `unused*` 前缀 | （删除） | XNALaraMesh 把其移到隐藏层 |
| `*twist*`、`*adj*`、`*ctr*` | （并入父骨或重映射到 捩） | Riveda："should be MERGED to their *parent* bones" |

唯一的实质分歧在躯干：Riveda、Hogarth CSV、Hogarth `boneMaps_renamer.py`、Model-To-PMX 都是 `pelvis → 下半身`、`spine lower → 上半身`、`spine upper → 上半身2`（[boneMaps_renamer.py](https://raw.githubusercontent.com/Hogarth-MMD/bones_renamer/master/boneMaps_renamer.py)；[Model-To-PMX README](https://raw.githubusercontent.com/SaraKale/Model-To-PMX/main/README.md)），而 Convert-to-MMD 的 `xna_lara.json` 把 `spine lower` 填进 `lower_body_bone`（下半身）、`upper_body_bone` 留空、`spine upper` 作 上半身2（[Convert-to-MMD presets](https://github.com/uitcis/Convert-to-MMD)）。后者只在模型没有 `pelvis` 时才说得通。建议：预设默认取多数派（`pelvis → 下半身`），当 `pelvis` 不存在而 `root hips` 带权重时自动把 `root hips` 当作 下半身 并另造无权重的 センター，同时在 UI 中把 `下半身` 槽标为"需确认"；该规则本身暴露为预设里可改的一行。VRM Add-on 的 `mmd_mapping.py` 把 HIPS 取 `センター` 而非 `下半身`（[mmd_mapping.py](https://github.com/saturday06/VRM-Addon-for-Blender/blob/main/src/io_scene_vrm/common/human_bone_mapper/mmd_mapping.py)），提醒我们内部模型里"Hips（变形）"与"センター（控制）"必须是两个槽。

### 三级匹配：精确预设 → 归一化词表 → 拓扑搜索，结果带置信度

**第一级精确预设**覆盖未被作者改名的"XPS 通用名"模型，直接查表。**第二级归一化词表**处理游戏原骨名未改的模型（DOA5LR 的 `MOT_*`、Koikatsu 的 `cf_j_*`、Biped 的 `Bip001 *`、Source 的 `ValveBiped.Bip01_*`）。Cats 的管线是：日文先译英文，再 "Always uppercase at the start and after an underscore"，`' '`/`'-'`/`'.'`/`':'` 统一为 `_`，剥前缀（`ValveBiped_`、`Bip01_`→`Bip_`、`Character1_`、`Cf_J_`、`DEF_`、`Armature|`…）与后缀（`_Bone`、`_Le`→`_L`、`_Ri`→`_R`、`_Jnt`、`S0`），词表键值中的 `\Left`/`\L` 展开为左右两份后**小写比较**，并用 `bone_list_conflicting_names` 三元组做上下文消歧（例：`(['\LeftUpLeg'], '\LeftLeg', 'Knee_\L')`）（[Cats armature.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature.py)）。XPS 名 `arm left shoulder 1` 经此变为 `Arm_Left_Shoulder_1`，与词表条目吻合，证明 Cats 对 XPS 做过实测。VRM Add-on 的 `_canonicalize_bone_name` 更通用：全角→半角、`([a-z])([A-Z])` 拆 camelCase、小写、数字独立成段、按 `[-._: (){}[\]<>]+` 分词、`("l","左")→"left"`、`("r","右")→"right"`，匹配时还要求"沿父链向上第一个已映射骨 == 规范父骨"才计分，然后对 16 套预设取 `(required_count, all_count)` 最大者（[human_bone_mapper.py](https://github.com/saturday06/VRM-Addon-for-Blender/blob/main/src/io_scene_vrm/common/human_bone_mapper/human_bone_mapper.py)）。建议把 Cats（MIT）/Rokoko（LGPL-3.0，与 Cats 同源）的别名表作为第二级词表数据，归一化函数采用 VRM 风格，侧别用 `\L` 通配。

**第三级拓扑/几何搜索**只在必需骨仍缺时触发，三个公开实现值得合并。Godot 4 的 `BoneMapper::auto_mapping_process` 顺序严格为 Root → Hips → 腿 → 足 → 脚趾 → 肩/臂 → 手 → 手指 → 脊柱 → Chest → Neck → Head → 眼/颌；Hips picklist 为 `hip, pelvis, waist, torso, spine`，找不到 Hips 则整体放弃；手先要求"恰有 5 个子骨"再放宽；手指链 ≥3 段取末 3 段（`search_path.slice(-3)`）避开腕骨；脊柱细分按 Chest 回溯到 Hips 的祖先数 0/1/≥2 决定 `Spine` / `Spine+Chest` / `Spine+Chest+UpperChest`；眼睛正则 `eye(?!.*(brow|lash|lid))`；左右完全靠名字 `(?<![a-zA-Z])left` / `(?<![a-zA-Z0-9])l(?![a-zA-Z0-9])`（[Godot bone_map_editor_plugin.cpp](https://github.com/godotengine/godot/blob/4.3/editor/plugins/bone_map_editor_plugin.cpp)）。VRM 的 `structure_based_mapping.py` 是唯一公开的纯打分方案：坐标按全局最大值做带符号开方归一化 `copysign(sqrt(|x|/max_x), x)`，必需骨 +1000、可选骨 +20、深度惩罚 `-sqrt(depth)`、`z>0` +5、中轴骨加 `z - |x|`、左臂 `x/2`、右臂 `-x/2`、脊柱链父子且父更低各 +5，允许 `skip_count` 个中间骨，搜索上限 1,000,000、递归深度 50（[structure_based_mapping.py](https://github.com/saturday06/VRM-Addon-for-Blender/blob/main/src/io_scene_vrm/common/human_bone_mapper/structure_based_mapping.py)）。MMD Tools Append 的 `detect()` 则是面向拆包骨架的几何法：只看 `use_deform` 且有权重的骨；手 = 子骨数 ≥ `finger_count-1` 且 |head.x| 最大者；手指按 `head.y` 排序赋 Thumb→Little；臂链用 `traverse_parent_chain`（方向夹角阈值 0.8）；胸 = 两手最近公共祖先（|vector.x| < 0.1）；脚趾 = head.z 最低且 `tail.y < 0`；`is_left = head.x > 0`；要求模型面朝 −Y（[humanoid.py](https://raw.githubusercontent.com/MMD-Blender/blender_mmd_tools_append/main/mmd_tools_append/converters/armatures/humanoid.py)）。推荐的组合是：先按权重统计区分变形骨/控制骨，Hips = 第一个具有"两条向下镜像分支 + 一条向上分支"的节点，再沿"子树权重最大者"下行取腿链、上行取脊柱链到左右肩的公共祖先，手指取末 3 段，眼睛用 Godot 正则加位置对称；名称只作软加分，最后用 VRM 式打分输出 `score_top1 / score_top2 / 来源(name|topology|position)`，`top1 − top2 < margin` 的槽标"歧义"，父链与规范不一致标 ERROR，必需骨缺失标 MISSING 并转入生成流程（对应 Godot 的 UNSET/MISSING/ERROR 三态）。

侧别判定应综合三种信号而不是只信名字：名字（`left/right`、`.L/.R`、`_L/_R`、`左/右`、`J_Bip_L_`，Convert-to-MMD 的规则表 `('Left','Right'), ('L_','R_'), ('-L','-R'), ('.L','.R'), ('_L','_R'), ('左','右'), (' L',' R')` 按序首个命中即替换）（[preset_operator.py](https://github.com/uitcis/Convert-to-MMD/blob/main/operators/preset_operator.py)）、骨头 X 坐标符号（Convert-to-MMD 与 MMD Tools Append 都以 `head.x > 0` 为左，前提是模型面朝 −Y——XPS 导入后恰好满足）、以及镜像配对（X 取反后最近邻距离小于 0.05×身高）。Cats 对 XPS 还有一条经验：Hips 世界坐标为负且非 FBX 时绕 X 轴旋转 180°（"Check if bone matrix == world matrix, important for xps models"）（[Cats armature.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature.py)），自写读取器按 `(x, -z, y)` 导入可避免这类翻转。

**映射数据格式**建议采用双层：内部规范槽位 = VRM 1.0/Unity 的 55 骨（`hips, spine, chest, upperChest, neck, head, left/rightEye, jaw, 四肢, 5 指×3`，拇指为 `Metacarpal/Proximal/Distal`）加 MMD 控制骨槽（`全ての親/センター/グルーブ/腰/操作中心/足ＩＫ/つま先ＩＫ/足IK親/肩P/肩C/腕捩/手捩/足D/足先EX/両目`），每槽带 VRM 式 `requirement / parent_requirement / 固定父骨`（[VRMC_vrm-1.0 humanoid.md](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md)）；每个模型的映射结果存为 `{slot_id: blender_bone_name}` JSON（VRM Add-on 的 Save/Load Bone Mappings 与 Convert-to-MMD 的 `CTMMD.json` 都是这种形状）；体系预设存为 `{slot_id: [alias, ...]}` JSON 并支持 `\L` 侧别通配；额外兼容读取 XPS 社区的 `BoneDict.txt`（逐行 `原始骨名;通用骨名`，XPS 10.9.4 起放在 `XNALara XPS.exe` 同目录即可实时改名，XNALaraMesh 用 `split(';')` 恰两段解析）（[XNALaraItalia 10.9.4](https://www.deviantart.com/xnalaraitalia/journal/XPS-10-9-4-Wardrobe-Edition-349764705)；[read_ascii_xps.py](https://github.com/johnzero7/XNALaraMesh/blob/master/read_ascii_xps.py)）；并像 Rokoko 那样把用户的手工修正学习进 `custom_bone_list.json`，下次自动识别优先命中（[Rokoko custom_schemes_manager.py](https://github.com/Rokoko/rokoko-studio-live-blender/blob/master/core/custom_schemes_manager.py)）。原 XPS 骨名应保留到 `mmd_bone.name_e`（Model-To-PMX 的 "ensuring no data loss" 做法）与自定义属性，便于回溯。注意 **Riveda 的 BoneDict 翻译文件声明 "don't redistribute"，不能内置**；其参考列表的名字本身只是事实陈述，可据此自建表（[Riveda translator](https://www.deviantart.com/riveda1972/art/XNALara-2-MMD-Bones-names-translator-UPD-1-10-630415138)）。

### 剩余骨的三种去向：删、并、留

游戏模型里不在人形集合内的骨分三类处理。**`unused*` 与整条无顶点组引用的子链**：XNALaraMesh 导入时把 `name.lower().startswith('unused')` 的骨和"整条链上没有任何子网格顶点组引用"的骨移到隐藏层（[import_xnalara_model.py](https://github.com/johnzero7/XNALaraMesh/blob/master/import_xnalara_model.py)），mmd_tools_helper 的 `delete_unused` 则把名含 `unused`（大小写不敏感）的骨与顶点组一并删除（[miscellaneous_tools.py](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/mmd_tools_helper/miscellaneous_tools.py)）——建议默认删除，但层级根（`root ground`/`root hips`）与 MMD 控制骨必须在白名单里：Cats 的 `delete_zero_weight` 跳过 `dont_delete_these_bones` 与名含 `Root_` 的骨（[Cats common.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/common.py)），Nuthouse01 的 `prune_unused_bones` 把"有非零权重、被刚体引用、被已用骨作父/表示先/付与親、是 IK 骨或其目标/链"都算 USED，并保护 `["メガネ","左ダミー","右ダミー","左手ダミー","右手ダミー","操作中心","全ての親","エッジ調整","LS_Center"]`（[prune_unused_bones.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/overall_cleanup/prune_unused_bones.py)）；Convert-to-MMD 本地版因缺白名单会误删 センター/IK，上游已加 `get_mmd_bone_whitelist` 修正（[Convert-to-MMD](https://github.com/uitcis/Convert-to-MMD)）。

**twist / adj 辅助变形骨**：Cats 的 `bone_reweigth_to_parent` 列表（`ArmTwist_\L`、`Arm_\Left_Shoulder_Adj_1..4`、`Arm_\Left_Elbow_Adj_1..4`、`Leg_\Left_Knee_Adj_1..4`、`Knee1_\L…Knee7_2_\L`、`AbdomenLower`、`ChestUpper`、`Back_Low/Mid`）沿父链找到第一个非列表骨，用 `VERTEX_WEIGHT_MIX`（`mix_mode='ADD'`, `mix_set='B'`）并入后删骨、子骨改挂（[Cats armature.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature.py)），与 Riveda "MERGED to their parent bones" 的建议一致。但并回单骨会丢失扭转分布，若目标 PMX 要有准标准 `腕捩/手捩`，更好的做法是先并回 腕/ひじ，再用下一小节的 ssb 公式重新生成并分配权重；Cats 的 `fix_twist_bones` 给出的反向比例（`*Twist1/2/3` 按 25/50/75% 并入主捩骨、75/50/25% 并入父骨）可作为"XPS 多段 twist → 腕捩1/2/3"直接重映射的参考（[Cats common.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/common.py)）。注意 MMD Tools Append 的 `add_leg_ik` 在 `ひざ` 的父不是 `足` 时会 `dissolve_bone` 吸收腿部 twist（[humanoid.py](https://raw.githubusercontent.com/MMD-Blender/blender_mmd_tools_append/main/mmd_tools_append/converters/armatures/humanoid.py)），Hogarth 也警告 "Leg twist bones and other non-standard leg or foot bones, with few exceptions, make a mess out of MMD leg-foot IK"（[Hogarth armature notes](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/tutorials%20MMD%20standard%20armature/MMD%20standard%20armature%20notes.txt)）——腿部 twist 应一律并回。

**有权重的非人形骨**（头发、裙、尾巴、武器、乳）：保留原名、挂到最近的人形父骨、放进 `その他`/`物理` 表示枠（Convert-to-MMD 把未归组骨放入 `other` 集合的先例）（[bone_map_and_group.py](https://github.com/uitcis/Convert-to-MMD/blob/main/bone_map_and_group.py)）。识别启发式：从 `頭`/`下半身`/`上半身` 悬挂、≥3 段、无镜像配对或兄弟数 ≥4、整体向下的叶链 → 物理骨候选；根不在 Hips 子树、或权重顶点全部落在身体 AABB 外 → 道具，挂到 `左/右手首`；乳骨照 Cats 保留 `Breast_L/R` 并挂到 `上半身2`。killinux/xps_to_mmd 在 Inase 模型上把 XPS 辅助骨 `xtra04/02/08`、`boob` 原样保留、未用辅助骨按最近变形骨分配权重（[xps_to_mmd README](https://raw.githubusercontent.com/killinux/xps_to_mmd/main/README.md)）。

### 补骨：用 あにまさ式实测比例放标准骨，用 ssb 公式生成准标准骨

「標準ボーン」的定义是 MMD 自带 あにまさ式初音ミク 去掉服装/头发骨后的集合，社区称 64 根；準標準ボーン 则是模型/动作作者为提高自由度而推广的附加骨，"完全には標準化できていないようだ"（[scrapbox 標準ボーン](https://scrapbox.io/motoso/%E6%A8%99%E6%BA%96%E3%83%9C%E3%83%BC%E3%83%B3)）。本次直接解析 three.js 随附的 あにまさ式 ver.2.3 `miku_v2.pmd`（140 骨，顶点 Y 范围 0.031～**20.214**）得到精确坐标，可按身高比例 H 把骨放到任意模型的地标上（[miku_v2.pmd](https://github.com/mrdoob/three.js/tree/r100/examples/models/mmd/miku)）。下表数值为【实测】，比例列为由实测除以 H=20.214 的【推导】：

"The center(センター) bone does not have any vertex group. The root(全ての親) bone ... does not have any vertex group. The eyes(両目) bone does not have any vertex group. The 4 leg and foot IK bones also do not have any vertex group ... Every other bone in an MMD standard armature has a vertex group."（[Hogarth armature notes](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/tutorials%20MMD%20standard%20armature/MMD%20standard%20armature%20notes.txt)）——这决定了 XPS→MMD 的生成规则：センター/グルーブ/両目/IK/足IK親/肩P/肩C/腰/腰キャンセル 全是**无权重控制骨**，只需位置与父子；真正要动权重的只有 上半身2、腕捩/手捩、足先EX、親指０ 以及缺失的 首/つま先/目。缺 首 时沿用 Cats 规则 `neck.head = chest.tail; neck.tail = head.head`（[Cats armature.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature.py)）；缺 つま先 时取 足首 组中沿脚前向投影最远的顶点簇，骨放在其 AABB 前端中心、Y 取地面；眼球若是独立网格/材质则取其包围球中心作 左目/右目 并整体 BDEF1（排除 `highlight|hilight|shine` 高光片），両目 置于两眼中点前上方——这几条是本调研的【推断】而非现成实现。

准标准骨的权威生成规则来自 そぼろ 的「準標準ボーン追加プラグイン」（PMD 版 ver 4.2、PMX 版 ver 1.4，2012-10-06 发布；dll 名 `SemiStandardBonesPMX.dll`，放入 PMXE `_plugin/User`）（[VPVP wiki PMDエディタ用プラグイン](https://w.atwiki.jp/vpvpwiki/pages/228.html)）。原版闭源，但 nanoem 作者 hkrn 把它完整移植为开源 C++ `plugin_ssb`，自述与原版「ほぼ同じ機能」，1.3.0（2021-02-14），并明确「『必要なボーン』は『日本語』のボーン名で判定します」「全角英数字と半角英数字を区別します」（[nanoem 插件文档](https://nanoem.readthedocs.io/ja/latest/plugin.html)）。以下逐骨规格全部出自其源码 `ssb.cc`（`mix(a,b,t)=a+(b−a)t`；`isVertexDedicatedByBone` 默认阈值 **0.97**；位置均为 PMX 坐标）（[nanoem ssb.cc](https://github.com/hkrn/nanoem/blob/main/emapp/plugins/ssb/ssb.cc)）：

| 骨 | 位置公式 | 父 / 层级重排 | 付与・軸・标志 | 権重处理 |
|---|---|---|---|---|
| 腕捩（`P=腕, C=ひじ`） | 勾选「回転自動補正」时 `C'.z += 0.75×(mean_z(权重≥0.6 属于 P 的顶点) − C.z)`；`O = mix(P, C', 0.6)`；`axis = normalize(C' − P)` | 父=腕；**ひじ 改父为 腕捩** | 軸固定 = axis；rot\|vis\|ctrl | 见下行 |

对话框默认值（nanoem 移植版 `loadWindowLayout()`）：腕捩/手捩/上半身2/腰/足IK親/足先EX/ダミー/肩キャンセル/親指０/グルーブ/全ての親/操作中心 全部默认勾选，只有「足Dボーンを操作可能に」默认关闭；带 `*` 的项会执行顶点权重再分配（[nanoem 插件文档](https://nanoem.readthedocs.io/ja/latest/plugin.html)）。日文教程的常用做法是「とりあえず全部チェック入れて追加」，且「おねがいダーリン」这类动作明确需要 グルーブ、上半身2、腰、肩P、腕捩、手捩、親指0（[さらりっち](https://karisakmmd.blog.jp/archives/8334623.html)）。原版插件**不生成 両目 与 首**（它们属标准骨，由 T0R0 的「標準ボーンチェッカー」负责）。两处可对比的分歧：あにまさ原模型自己的 腕捩 位于 腕→ひじ 的 t≈0.353、手捩 ≈0.265（由坐标反算），与插件的 0.6 不同——两者都被广泛使用，说明 VMD 兼容性对捩骨位置不敏感，位置主要影响蒙皮效果，建议默认 0.6 并开放参数；上半身2 的 0.35 同理可调。一次性生成全部骨时可直接按最终结构写出：`操作中心 > 全ての親 > センター > グルーブ > 腰 > {上半身 > 上半身2 > 首 > 頭 …, 下半身 > 腰キャンセル左/右 > 足 …}`，D 链挂在 腰キャンセル（或 下半身）之下。权重分割的通用内核（沿父骨轴投影 + smoothstep 过渡，半宽建议 0.15～0.25×骨长【推断】，排除物理/头发顶点组——对应 そぼろ 插件的「物理ボーン除外 / 材質選択」）在 Blender 中应用纯 Python `VertexGroup.add(..., 'REPLACE')` 实现而非 `VERTEX_WEIGHT_MIX` 修改器（带形态键的网格无法应用修改器），分割后必须 `vertex_group_limit_total(limit=4)` + `normalize_all(lock_active=False)`，因为 mmd_tools 导出按组数选 BDEF1/2/4，>4 组时取前 4 大并归一化（[mmd_tools exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)；[Blender object_vgroup.cc](https://github.com/blender/blender/blob/main/source/blender/editors/object/object_vgroup.cc)）。

### IK、付与、変形階層、ローカル軸与骨序：数值全部有一次来源

**腿 IK** 的实测与规范值高度一致。ver.2.3 PMD：`左足ＩＫ target=左足首 chain=['左ひざ','左足'] iterations=40 control_weight=0.5`；`左つま先ＩＫ target=左つま先 chain=['左足首'] iterations=3 control_weight=1.0`（[miku_v2.pmd](https://github.com/mrdoob/three.js/tree/r100/examples/models/mmd/miku)）。PMX 规范把单位角存为弧度且「PMDのIK値とは4倍異なるので注意」，故 0.5→**2 rad = 114.5916°**、1.0→**4 rad = 229.1831°**；IK loop「PMD及びMMD環境では255回が最大」（[PMX仕様.txt](https://gist.github.com/FlandreDaisuki/90ae5abf3138a15994526b6bfec73c2c)）。Hogarth 的 IK 笔记给出同样的 PMX 口径：つま先ＩＫ "Loop count: 3 … Unit angle: 229.1831 … Angular limits should not be enabled"；足ＩＫ "Loop count: 40 … Unit angle: 114.5916 … Angular limits must be enabled on the knee bone … x -180 -0.5, y 0 0, z 0 0"，IK 骨与 足首 同位、尾朝后，つま先ＩＫ 与 つま先 同位、尾朝下（[Hogarth IK notes](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/tutorials%20MMD%20standard%20armature/MMD%20leg-foot%20IK%20notes.txt)）；其随附的 ver.1.3 PMX 骨架实际为 loop 48 / 6，来源差异未考证。MMD 作者关于 7.38+ 的说明：「角度制限付きIKを正確に計算するためにターゲットボーン方向を向くまで Loop回数以上ループする場合があります」，单位角过小会极慢，「MMDを使う場合はIKの単位角は1以上に設定してください」（[VPVP wiki PMXの概要](https://w.atwiki.jp/vpvpwiki/pages/284.html)）。CCD 需要知道膝盖弯向：ver.2.3 的 足→ひざ 与 ひざ→足首 夹角 4.0°，Cats 在膝与大腿重合时把膝沿 Y 前移 0.001（[Cats armature.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature.py)）。推荐写出：`左足ＩＫ` flags `0x003E`（回転|移動|表示|操作|IK），loop 40，unit 2.0 rad，links `[左ひざ{limit on, min=(−π,0,0), max=(−0.5°=−0.0087266 rad,0,0)}, 左足{off}]`；`左つま先ＩＫ` loop 3，unit 4.0 rad，links `[左足首{off}]`。其他工具的取值仅供对照：Hogarth 脚本 iterations 48/6、`ik_rotation_constraint` 膝=2 踝=4、`LIMIT_ROTATION` `min_x=math.pi/360` `max_x=math.pi`（[add_foot_leg_ik.py](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/mmd_tools_helper/add_foot_leg_ik.py)）；MMD Tools Append 200/15；Convert-to-MMD 200/200 且 `ik_max_x=180°`。

在 mmd_tools 中表示腿 IK 的方式镜像其导入器：**IK 约束放在链首骨 `左ひざ` 上**，`target=骨架, subtarget="左足ＩＫ", chain_count=2, iterations = loopCount × mmd_root.ik_loop_factor`（导入默认因子 5，新建 root 默认 1）；单位角写 `左ひざ.mmd_bone.ik_rotation_constraint`（弧度，属性默认 **1**，不能依赖默认）；在 `左足首` 上加静音 `DAMPED_TRACK` 约束 **`mmd_ik_target_override`**（`subtarget=左ひざ`）明确 target；膝限制优先用 `LIMIT_ROTATION` 约束 **`mmd_ik_limit_override`**（`owner_space="LOCAL"`，开 `use_limit_x`），它在导出选项 `ik_angle_limits=EXPORT_ALL`（默认）下优先级最高；`左足首` 上再建 `chain_count=1` 的 IK 指向 `左つま先ＩＫ`（[mmd_tools importer.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/importer.py)；[mmd_tools exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。Hogarth 提醒 "Normally an MMD model does not have any arm/hand IK and adding hand/arm IK may cause incompatibility with VMD motions"（[Hogarth IK notes](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/tutorials%20MMD%20standard%20armature/MMD%20leg-foot%20IK%20notes.txt)），插件不应生成手臂 IK。

**付与（Rotate+/Move+）**在 Blender 侧由 `mmd_bone.has_additional_rotation / additional_transform_bone / additional_transform_influence` 描述；`FnBone.apply_additional_transformation` 会创建 TRANSFORM 约束 `mmd_additional_rotation`（from/to ∓π，to 乘 influence，`influence<0` 时 `from_rotation_mode="ZYX"`）与 `_dummy_<bone>` / `_shadow_<bone>` 影子骨（分别进 `mmd_dummy` / `mmd_shadow` 集合，`is_mmd_shadow_bone=True` 不导出）；导出时 `hasAdditionalRotate` 仅在 `additional_transform_bone` 非空时为真（[mmd_tools core/bone.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/bone.py)）。需要写入的付与率：左目/右目 源=両目 率 1.0；腕捩1/2/3 源=腕捩 率 0.25/0.5/0.75；肩C 源=肩P 率 −1；腰キャンセル 源=腰 率 −1；足D 系 源=原骨 率 1。

**変形階層**：PMX 变形顺序为「1. 物理前／後 2. 階層順 3. Index順」，付与「付与親の変形前にボーン変形が呼び出されても正常に変形する(ただし1段階のみ)」（[PMX仕様.txt](https://gist.github.com/FlandreDaisuki/90ae5abf3138a15994526b6bfec73c2c)）。普通骨设 0；回転付与骨放在付与親之后（同层靠 Index）即可，或按 PMD→PMX 官方转换惯例把 IK 链设 1、回転影響下 设 2；足D 链按 ssb 设「原骨 +1」；Nuthouse01 的 auto-armtwist 脚本用 D 2 / T 3 / 子捩 4 属非标准做法（[bone_add_semistandard_auto_armtwist.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/scripts_for_gui/bone_add_semistandard_auto_armtwist.py)）。mmd_tools 的 `transform_order`（0–100）与 `transform_after_dynamics` 直接对应，`realign_bone_ids` 的排序键会把"同层且父 id ≥ 子 id"的骨挪到祖先之后（[mmd_tools core/model.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/model.py)）。

**ローカル軸 / 軸固定**不影响变形，只影响操作：规范明文「0x0400 軸固定 / 0x0800 ローカル軸 は、表示及び操作時の制限項目になる。ボーンの変形特性や内部値には関与しない」（[PMX仕様.txt](https://gist.github.com/FlandreDaisuki/90ae5abf3138a15994526b6bfec73c2c)），但 XPS 没有 roll，所以手臂/手指的局部轴必须由插件计算。约定：X = normalize(子骨 − 本骨)，Z 取与 X 正交且尽量接近 PMX 前后轴 (0,0,±1) 的向量，Y = Z × X；Nuthouse01 的 `bone_set_arm_localaxis.py` 对 肩/肩P/腕/腕捩/ひじ/手捩/手首 正是如此，并给捩骨 `fixedaxis = normalize(ひじ − 腕)`，共线容差 0.0001（[bone_set_arm_localaxis.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/scripts_for_gui/bone_set_arm_localaxis.py)）；mmd_tools 的 `update_auto_bone_roll` 在 X–Z 正面平面内取与骨投影垂直的参考边，自动名单 `AUTO_LOCAL_AXIS_ARMS = ("左肩","左腕","左ひじ","左手首","右腕","右肩","右ひじ","右手首")`、`AUTO_LOCAL_AXIS_FINGERS = ("親指","人指","中指","薬指","小指")`、`AUTO_LOCAL_AXIS_SEMI_STANDARD_ARMS = ("左腕捩","左手捩","左肩P","左ダミー",…)`（[mmd_tools core/bone.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/bone.py)）。写入时 `mmd_bone.enabled_local_axes=True; local_axis_x/z = PMX 坐标向量`（Blender 向量 `.xzy`），捩骨 `enabled_fixed_axis=True`；左右臂 Z 符号同向还是镜像没有一手文档，应用 あにまさ模型的实际 `localaxis` 值做回归测试后固定。

**骨序与表示枠**：导出严格按 `bone_id`，插件应按目标顺序直接写入 0..N−1 再跑一次 `mmd_tools.fix_bone_order` 保险；IK 骨不受 `realign_bone_ids` 移动（它只看父子/付与），顺序完全由我们控制。表示枠推荐：`Root`(special)[全ての親]、`表情`(special)[全部モーフ]、`センター`[操作中心, センター, グルーブ, 腰]、`ＩＫ`[左足IK親, 左足ＩＫ, 左つま先ＩＫ, 右…]、`体(上)`[上半身, 上半身2, 首, 頭, 左目, 右目, 両目]、`腕`[左肩P, 左肩, 左腕, 左腕捩, 左ひじ, 左手捩, 左手首, 左ダミー, 右…]、`指`、`体(下)`[下半身]、`足`[左足, 左ひざ, 左足首, 左つま先, 左足先EX, 右…]、`髪`/`スカート`/`その他`；D 骨、肩C、腰キャンセル、腕捩1〜3 不登记。这与 ver.2.3 的枠顺序 ＩＫ, 体(上), 髪, 腕, 指, 体(下), 足 及 Nuthouse01 `dispframe_fix` 的规则（Root 枠只放 全ての親、缺 センター 枠则在 index 2 新建并放 操作中心/センター/グルーブ/腰、删面板 0 モーフ与重复项、补入未注册的可见骨、`MAX_MORPHS_IN_DISPLAY = 250`）一致（[dispframe_fix.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/overall_cleanup/dispframe_fix.py)）。在 mmd_tools 中最省事的做法是先把骨骼归入同名骨骼集合，再调 `FnBone.sync_display_item_frames_from_bone_collections(arm)` + `FnModel.initalize_display_item_frames(root, reset=False)`，注意 XPS 导入器创建的其它集合会被一并变成枠，需事先清理（[mmd_tools operators/display_item.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/display_item.py)）。

### 手动修复：把每个自动步骤都做成可逆、可局部重跑的操作

所有可手改的现成工具都用 Blender `prop_search` 逐槽选骨，差别只在布局与防呆：Convert-to-MMD 每槽一行"日文骨名标签 + `ZOOM_SELECTED` 取选中骨按钮 + `prop_search`"，对称骨一行两槽、手指一行三槽，预设下拉即时加载、JSON 导入导出（[Convert-to-MMD](https://github.com/uitcis/Convert-to-MMD)）；Expy Kit 左右两列 `sided_rows` 加 "<-" `SetToActiveBone` 与列头镜像按钮（[Expy Kit ui.py](https://github.com/pKrime/Expy-Kit/blob/main/ui.py)）；VRM Add-on 分 Required/Optional，候选只列"最近已指派祖先的后代，排除已指派给其他人形骨的骨及其祖先/后代分支"，并有一键 "Automatic Bone Assignment"（用户已填的必需骨多于自动结果时 `CANCELLED`）（[VRM vrm1/panel.py](https://github.com/saturday06/VRM-Addon-for-Blender/blob/main/src/io_scene_vrm/editor/vrm1/panel.py)）；MMD Tools Append 按 `DISPLAY_TYPE_COLUMNS = {"DEFAULT": 1, "MIRRORED": 2, "FINGER": 3}` 分列并用 `auto()` 补全镜像/指节（[humanoid.py](https://raw.githubusercontent.com/MMD-Blender/blender_mmd_tools_append/main/mmd_tools_append/converters/armatures/humanoid.py)）。建议合并这些模式：VRM 式分组与候选过滤 + Convert-to-MMD 式取选中骨 + Append 式镜像/手指列 + Godot 式 UNSET/MISSING/ERROR 着色与歧义标记。

修复操作清单（均应在不重新导入的前提下可重跑）：① **映射槽改一处即局部重算**：改名、顶点组同步、`name_e` 回填、受影响的生成骨重定位；② **权重工具**：Cats 式"并入最近未选中父骨 / 并入活动骨"（`MergeWeights` 对每根选中骨 `while parent in selected: parent = parent.parent` 后 `mix_weights`，`keep_merged_bones` 可保留骨）（[Cats armature_manual.py](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature_manual.py)）、"沿骨轴分割（带分界位置/过渡半宽预览）"、"未匹配骨按最近变形骨分配"、零权重顶点三级回退（邻域平滑 → Data Transfer `Nearest Face Interpolated` → 最近骨 BDEF1）；③ **骨架备份**：重命名前复制为 `{obj.name}_backup` 并隐藏（Convert-to-MMD 2.6 做法），任何阶段可整体回退；④ **复用 mmd_tools 面板**：Bone Order（`mmd_tools.bone_id_move_top/up/down/bottom`、`fix_bone_order`，并以 `ERROR` 图标显示父/付与亲 rank 违规）、Display Panel Quick Setup（`RESET/FACIAL/GROUP_LOAD/GROUP_APPLY`）、Model Debug（`validate_bones/morphs/textures` 与 `fix_*`）、Material/Meshes Sorter、`mmd_tools.translate_mmd_model`（`types={"BONE"}, modes={"MMD"}` 自动补 `name_e`）、`mmd_tools.bone_local_axes_setup` / `bone_fixed_axis_setup`（`LOAD/APPLY/DISABLE`）（[mmd_tools operators/model.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/model.py)）；⑤ **姿态**：臂角滑杆重烘（见下节）；⑥ **物理**：以我们的预设调用 `mmd_tools.rigid_body_add` / `joint_add`；⑦ **VMD 回归**：`mmd_tools.import_vmd` 载入标准动作后在 Blender 内比较各标准骨朝向与参考模型的偏差（Convert_to_MMD5 的 "rotation errors ≤12°" 判据可作起点）。

## 静置姿态、缩放与坐标：把社区的分歧做成参数，而不是常数

T 姿势模型直接套 A 姿势动作会把双臂整体抬高，原因在格式层面：PMX 骨记录只有位置、父、层级、旗标、尾、付与、固定轴、局部轴与 IK，**没有静止旋转字段**，而 VMD 以四元数记录「相对初始姿态、在父骨坐标系中的旋转」，mmd_tools 导入 VMD 时用 `bone.matrix_local`（Y/Z 行交换）做相似变换且不引用任何 local_axis 属性（[mmd_tools core/vmd/importer.py](https://github.com/UuuNyaa/blender_mmd_tools/blob/main/mmd_tools/core/vmd/importer.py)）。DanceXR 的工程解释最直白："The VMD motion defines how much rotation needs to be applied to each bone but it doesn't specify what the original orientation of the bone is"，因此它提供 "Standard Pose Angle" 滑杆让用户微调（[DanceXR 1.3.6 devlog](https://stormlab.itch.io/dancexr/devlog/439796/release-136)）。于是每一帧都带常量误差 δ = ∠(T 臂向, A 臂向)，唯一的修正办法是把网格与骨骼位置一起旋转到 A 姿势再导出，ローカル軸 帮不上忙（规范明文其不参与变形）。

角度数值上社区并无共识，而一次数据给出了精确基准。あにまさ式 ver.2.3 实测：左肩→左腕 低于水平 30.24°（长 0.875）；**左腕→左ひじ 29.72°**（长 3.109）；**左ひじ→左手首 40.28°**（长 2.201）；左腕→左手首 整臂 34.09°（长 5.288）；肘弯 10.57°；膝弯 4.00°，大腿偏竖直 1.48°；手首→中指１ 方向 (0.877, −0.762, −0.042)、拇指在 −Z 前侧（[miku_v2.pmd](https://github.com/mrdoob/three.js/tree/r100/examples/models/mmd/miku)）；ver.1.3 骨架反算约 31.4° / 40.2°（[Hogarth PMX 骨架](https://github.com/Hogarth-MMD/mmd_tools_helper/tree/master/pmx%20example%20armatures)）。社区取值则分散：Hogarth 泛称 "approximately 45 degree angle in an A-pose"（[Hogarth armature notes](https://github.com/Hogarth-MMD/mmd_tools_helper/blob/master/tutorials%20MMD%20standard%20armature/MMD%20standard%20armature%20notes.txt)）；pingpongfrog 的 Blender 教程以 3D 游标为轴把腕骨绕 Y 旋转 45°（[pingpongfrog #7](https://pingpongfrog.com/archives/1653)）；Convert-to-MMD 对上臂施加 `Matrix.Rotation(radians(±37), 4, 'Y')`（[Convert-to-MMD](https://github.com/uitcis/Convert-to-MMD)）；一个 2026 年的重定向项目写死 `MMD_STANDARD_ARM_REST_DEGREES = 34`，上臂承担偏移、前臂/手/手指做共轭变换（[krapnikkk/retarget #16](https://github.com/krapnikkk/retarget/issues/16)）；MillionDance 把 "Convert T-pose … to TDA-styled 'A-pose'" 做成开关（[MillionDance Manual](https://github.com/OpenMLTD/MLTDTools/wiki/MillionDance-Manual)）。日文解释也只说 A スタンス是「水平より若干下がった角度」，角度不符时「高く上がり過ぎで頭にめり込む、また逆に下過ぎて体に手がめり込む」，事后在 MMD 用「ボーンフレーム位置角度補正」补偿（[angelia 2020](https://angelia-sakuraryuusui.blogspot.com/2020/05/mmd-explaining-arm-angle.html)）。**推荐**：把目标姿态做成两个参数——上臂低于水平角 θ₁（默认 30°，【实测】あにまさ）与前臂附加下垂角 θ₂（默认 10°，即前臂 ≈40°），右臂镜像，附带预设 "あにまさ ver.2.3 (30/40)"、"通用 45°"、"37°（Convert-to-MMD）"；转换前先从已映射的 腕/ひじ 测出源模型实际臂角，已在目标 ±3° 内则跳过；腿保持近竖直但保证膝不与髋/踝精确共线（ver.2.3 的 4° 膝弯 / Cats 的 0.001 前移）；手掌朝下略内旋的滚转需单独校正，因为 `rotation_difference` 不约束绕骨轴的滚转。TDA 式等常见模型的实际臂角本次未测得，是已知空白。

实现上，Blender 的 `POSE_OT_armature_apply` 只改 edit bone 的 head/tail/roll 并清零 pose，不修改网格，还警告 "Actions on this armature will be destroyed by this new rest pose"（[Blender pose_transform.cc](https://github.com/blender/blender/blob/main/source/blender/editors/armature/pose_transform.cc)）；而带形态键的网格无法直接 `modifier_apply`——日文教程为此改用「シェイプキーとして保存」再替换 Basis，并警告「肩の変形が過剰になっています」（[pingpongfrog 3055](https://pingpongfrog.com/archives/3055)）。两条现成路线是 przemir/Cats 的"对每个 key 复制网格 → 应用 Armature → `join_shapes` 合回"（[przemir](https://github.com/przemir/ApplyModifierForObjectWithShapeKeys/blob/master/ApplyModifierForObjectWithShapeKeys.py)；[Cats PoseToRest](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/tools/armature_manual.py)），以及本调研推荐的矩阵法：对每根变形骨算 `S_i = pose_bone.matrix @ bone.matrix_local.inverted()`，每顶点 `M_v = Σ w_i S_i / Σ w_i`（无权重顶点用单位阵），对 Basis 与每个 key 的 `data[i].co` 施加同一 `M_v`，再 `bpy.ops.pose.armature_apply(selected=False)`——无 ops、不改顶点序、相对 key 关系自然保持。前提是权重已归一、网格只受该 Armature 修改器变形、自定义拆分法线按 `M_v` 旋转部分一并变换；执行顺序必须是 **先改 rest pose，再做权重分割/新骨生成，最后设 ローカル軸**。XPS 模型通常没有形态键，此时直接应用 Armature 修改器即可，矩阵法留给用户已加形态键的情形。

**缩放**同样没有权威常数。あにまさ式 ver.2.3 顶点最高 20.214，按官方身高 158 cm 得 **1 单位 ≈ 7.816 cm**【实测推算】；Hogarth 的口径是 "Miku herself is a little more than 20 MMD units tall … each unit measures 7.9 centimeters"，并提醒 "no one seems to know exactly"（[Hogarth 1 MMD unit](https://www.deviantart.com/hogarth-mmd/journal/1-MMD-unit-in-real-world-units-685870002)）；mmd_tools 导入默认 `scale=0.08`、导出 **12.5**（[mmd_tools fileio.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/fileio.py)）。XPS 一侧则**没有任何文档定义单位**：XNALaraMesh 的导入/导出坐标函数均无缩放因子，只能从 `MIN_BONE_LENGHT = 0.005`、根骨尾长 0.5、默认尾长 0.1 这些常量推断"近似米制"（【推断】），而社区教程里缩放 10 倍（powroupi wiki、ElodieS）与 12.5 倍（Convert_to_MMD5）并存，Model-To-PMX 则按包围盒归一化到 20 单位（[Model-To-PMX README](https://raw.githubusercontent.com/SaraKale/Model-To-PMX/main/README.md)）。由于 VMD 的 センター/足ＩＫ 平移是绝对单位，身高失配会导致步幅与脚 IK 不匹配（【推断】），**推荐默认按身高归一化**：测 `root ground`→头顶的包围盒高度，缩放到目标身高（默认 20 单位，用户可按角色改为 22–23 等），并提供"固定倍率（米制模型 12.5）"的覆盖项；缩放应在 `Model.create` 之前以对象变换应用到骨架与网格（mmd_tools 导出会烘焙 `matrix_world`，且所有对象 scale 必须为正，否则面绕序被额外反转）。

**坐标链**完全由两端的导入/导出器决定，无需插件额外旋转。XNA 是右手系、+X 右、+Y 上、+Z 朝向观察者（[Microsoft Learn XNA Vector3](https://learn.microsoft.com/en-us/previous-versions/windows/silverlight/dotnet-windows-silverlight/bb196940(v=xnagamestudio.35))）；XNALaraMesh 导入 `Blender (X, Y, Z) = (x_xps, −z_xps, y_xps)`，这是绕 X 轴 +90° 的纯旋转（行列式 +1，无手性翻转），面索引 `[f0, f2, f1]` 翻转是因为 DirectX 以顺时针为正面，UV `v' = 1 − v`（[import_xnalara_model.py](https://github.com/johnzero7/XNALaraMesh/blob/master/import_xnalara_model.py)）；mmd_tools 导出 `(x, y, z) → (x, z, y)`。合成后 XPS→PMX 为 `(x, y, z) → (x, y, −z)`，与 Model-To-PMX 的固定反射一致；MMD 为左手系 Y-up，模型面向 −Z（ver.2.3 左つま先 Z=−2.464 相对 左足首 Z=0，両目先 Z=−1.5），VMD/PMD 数据「左手座標系(データは左手座標系。MMDの画面表示は右手座標系。)」（[kumiho_k VMD wiki](https://w.atwiki.jp/kumiho_k/pages/15.html)）。两个细节要记住：XPS 的 `.pose` 旋转以模型世界轴定义（Euler `'YXZ'`、角度制），导入默认姿势时需用 `matrix_local` 的旋转做相似变换进入骨骼局部空间（[import_xnalara_pose.py](https://github.com/johnzero7/XNALaraMesh/blob/master/import_xnalara_pose.py)）；XPS 格式**不存在**骨骼 roll/朝向，骨尾只能靠 `boneTailMiddle` 启发式（根骨尾 `head + (0, −0.5, 0)`；有子骨取可见非辅助子骨头部平均；无子骨沿"父尾→本头"延伸；最小长度 0.005），PMX 的接続先在"单一子骨且 head == 本骨 tail"时写子骨索引，否则写偏移向量——mmd_tools 在目标骨 head 与本骨 tail 距离 > 0.01 时会警告并退化为 OFFSET（[mmd_tools exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。

## 材质、表情、物理、校验：按社区默认值自动化，按开关升级

### 材质：只有 diffuse 能进 PMX，渲染组决定透明与排序

XPS 的材质信息全部编码在网格名与贴图列表里：`makeRenderType` 用 `_` 切分，第 0 段为数字即渲染组号，随后依次为 `meshName`、`specularity`（默认 1）、`texRepeater1/2`（默认 0），第 0 段非数字时默认 **RG 5**（[xps_material.py](https://github.com/johnzero7/XNALaraMesh/blob/master/xps_material.py)）；社区文档的格式说明是 `[RenderGroup]_[MeshName]_[Value1]_[Value2]_[Value3]`，Value1 为高光强度（默认 0.1）、Value2/3 为 bump 重复次数（[xnalara.forumotion Lesson 5](https://xnalara.forumotion.com/t71-lesson-5-what-is-render-groups)）。XNALaraMesh 内置 1–43 组，每组决定贴图槽顺序、`rgAlpha`、`rgShadding`（Yes / shadeless / Vertex）与 `rgPosable`：**alpha 组为 6、7、8、9、12、15、18、19、20、21、23、25、27、29、31、33、37、39、41、43**（35 未标 alpha，疑为上游遗漏）；**无光照组为 10、13、14、15、21**；顶点光照 11、12；贴图槽如 RG1 `diffuse, lightmap, bump, mask, bump1, bump2`，RG2 `diffuse, lightmap, bump`，RG22/23 七张含 specular，RG24/25 `diffuse, lightmap, bump, specular`（社区称 24/25 应改用 22/23、26/27 应改用 28/29），RG26–31 含 environment/emission，RG40–43 `diffuse, bump, specular`（[xps_material.py](https://github.com/johnzero7/XNALaraMesh/blob/master/xps_material.py)；[junkymana Render Groups](https://www.deviantart.com/junkymana/art/XNALara-XPS-Render-Groups-543000260)）。本地 B2XPS 1.1.0 自带的 10 组表与之不一致（RG 25/26 槽位错位），自写读取器不要照抄。XPS 还有 `+`/`-` 前缀（默认显示/隐藏可选项）、`|` 分组与 `.` 后缀（多网格合成一个菜单项），官方示例正是表情网格 `+ "FAU|happy"`、`- "FAU|neutral"`（[xnalara.org 可选项说明](http://xnalara.org/viewtopic.php?f=28&t=1678)）——XNALaraMesh 对这些前缀**不做任何处理**，自写读取器应解析并保留。

PMX 材质只持有 texture index、sphere index + 模式（0 关 / 1 乗算 / 2 加算 / 3 サブテクスチャ）、toon index + 共享标志（0=文件 / 1=内建 toon01～toon10）与 memo（[PMX 2.0 规范英译](https://gist.github.com/felixjones/f8a06bd48f9da9a4539f)），法线/高光/遮罩/自发光贴图没有槽位。MMD 可读 BMP、JPG（5.17+）、PNG（6.00+，含透明）、TGA、DDS（[VPVP wiki 拡張子](https://w.atwiki.jp/vpvpwiki/pages/322.html)）；`toon01.bmp～toon10.bmp` 是保留名，"If you use these names for your toons, MMD will ignore your files and use its own"（[LearnMMD](https://learnmmd.com/http:/learnmmd.com/know-about-pmd-pmx-textures/)）。贴图落盘规则：转 32bit PNG（透明）/ 24bit PNG，文件名只用 ASCII，放 `textures/` 一级子目录，写 PMX 前用 cp932 试编码所有名称与路径——Nuthouse01 与 mmd_tools 的 `validate_textures` 都这样做（[model_overall_cleanup.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/scripts_for_gui/model_overall_cleanup.py)；[mmd_tools model_validation.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/model_validation.py)）。mmd_tools 导出时**无论复制模式**都把路径改写为相对路径（无 `root["import_folder"]` 时为 `textures/<basename>`），`copy_textures_mode` 默认 `SKIP_EXISTING`（[mmd_tools exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。

绘制顺序是硬约束：「１つのモデルの中では材質ごとに、材質順に描画されます」，透明材质必须排在被它遮挡的材质之后（[ブロマガ 描画順](https://site.nicovideo.jp/ch/userblomaga_thanks/archive/ar234462)），MMD 规格「半透明素材の後に描写するものは、半透明素材に透過させない」（[MMDSupporter](https://note.com/mmd_supporter/n/n594976ba8d33)），脸部件惯例 アイライン → 眉毛 → 瞳 → 目のハイライト（[rio-vroidmmd](https://rio-vroidmmd.hatenablog.com/entry/2021/11/15/105821)）。推荐顺序：不透明主体 → 脸 → アイライン/眉 → 瞳 → 高光 → `rgAlpha` 材质（头发透明边、睫毛、玻璃）；mmd_tools 自带的 `sort_materials` 只按"到中心距离"排序且源码自称「かなりいいかげんな実装」、警告 "Will not work if you have transparent meshes inside the model"，不可依赖（[mmd_tools exporter.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/core/pmx/exporter.py)）。由于 mmd_tools 按对象名排序网格、同名材质跨网格合并，精确控制顺序的办法是给对象名加 `NNN_` 前缀（Meshes Sorter 的做法）或合并为单对象后按槽位排序。非 diffuse 贴图建议记录到材质 comment，例如 `[:XPS:] RG=22; bump=xxx.png; spec=yyy.png`，供 MME/Ray-MMD 用户手工接入——KKPMX 用 `[:Disabled:]`、`[:AccId:] XX` 等标记做过同样的事（[kkpmx_core.py](https://github.com/CazzoPMX/KKPMX/blob/master/src/kkpmx_core.py)）。

XPS 的 `+`/`-` 可选部件可映射为 材質モーフ 开关。Nuthouse01 的标准化模板：目标材质初始可见 → "hide" 用 **乗算×0**（alpha=0, edgealpha=0, edgesize=0, tex/sph/toon RGBA=[1,1,1,0]）；初始透明（alpha==0）→ "hide" 用 **加算 −1**，"appear" 用 加算 +1，并把隐藏材质的 edge alpha 置 0 由显示モーフ加回（只转移 edge alpha 不转移 edge size，避免叠加变粗），注释 "i know that zeroing out tex/toon/sph alpha IS correct because the 'alphamorph' PMXE plugin does it that way!"（[alphamorph_correct.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/overall_cleanup/alphamorph_correct.py)）。命名沿用 `<部件名> 透明化`（[khsk](https://github.com/khsk/mmd-add-transparency-morph)）或 `Show:<x>` / `Hide:<x>`（KKPMX），全部放「その他」面板并加入「表情」枠；`-` 前缀的默认隐藏部件导出为 alpha=0 材质 + 显示モーフ，`|` 分组可把多网格合成一个开关。

### 表情：XPS 零形态键，用占位名 + 骨骼モーフ + 材质モーフ搭出可用集

XPS 格式 "stores no blend shapes"（[Model-To-PMX README](https://raw.githubusercontent.com/SaraKale/Model-To-PMX/main/README.md)），表情在 XPS 生态里靠面部骨或可选网格实现；Riveda1972 的工具给 46 根面部骨（从 `head eyebrows middle` 到 `head cheek right 4`）生成 46 个基于骨的表情，前提是骨名完全一致（[Riveda facial expressions](https://www.deviantart.com/riveda1972/art/XPS-XNAlara-to-MMD-Facial-Expressions-UPDATED-595551582)）——完整名单在 DeviantArt 图片中，本次只拿到首尾两项。PMX 侧硬约束：面板 1 眉 / 2 目 / 3 口 / 4 その他，**0 为隐藏，放进表示枠会让 MMD 崩溃**，表示枠内モーフ须 <250（"if MMD has 256+ morphs among all display groups, it will crash"）（[dispframe_fix.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/overall_cleanup/dispframe_fix.py)）；VMD 以日文名匹配，骨/モーフ名固定 **15 字节 Shift-JIS**（全角 ≤7 字），超长截断后「0123456789012345と0123456789012346が同じ扱いになっちゃう」（[posfie](https://posfie.com/@tryme_/p/IX2iSDC)）。

核心表情集以 あにまさ式 ver.2.3 为基准（一次数据，30 个）：眉 真面目/困る/にこり/怒り/上/下；目 まばたき/笑い/ウィンク/ウィンク２/ウィンク右/ｳｨﾝｸ２右/はぅ/なごみ/びっくり/じと目/なぬ！；口 あ/い/う/お/▲/∧/ω/ω□/はんっ！/えー/にやり；その他 瞳小/ぺろっ（[miku_v2.pmd](https://github.com/mrdoob/three.js/tree/r100/examples/models/mmd/miku)）；日文社区明确「配布モーションは…あにまさ式ミクさんの表記…基準につくられている」，并把 **え** 标为必备（「ミク lacks it」）（[一護牛乳 表情一覧](https://mmd15gyuunyuu.blog.jp/archives/11193436.html)）；TDA 系扩展常见 はちゅ目/星目/はぁと/瞳大/ハイライト消し/口角上げ/口角下げ/頬染め/青ざめ（[しぐにゃも](https://signyamo.blog/3d-facial/)）。名称必须逐字节一致（含半角片假名 `ｳｨﾝｸ２右` 与全角数字）。

生成策略综合三个转换器的实践。KKPMX 把缺失的标准名以**空占位モーフ**补齐（`add_TDA`，EN="Placeholder"），眼睑闭合比例默认 0.66，并用 `generateWink` 把双眼モーフ拆左右（[kkpmx_morphs.py](https://github.com/CazzoPMX/KKPMX/blob/master/src/kkpmx_morphs.py)）；vroid2pmx 的「まばたき」实际是 **群モーフ**：绑定顶点モーフ + 眼皮骨 ボーンモーフ + 眉随动，「あ」= 群モーフ（`Fcl_MTH_A` 顶点改名 "あ頂点" 放面板 0 隐藏 + 下颌骨モーフ），星目/はぁと = 群モーフ（高光隐藏 + 独立材质的材質モーフ），并额外生成 上/下/眉左/眉右/瞳小/瞳大/エッジOFF 等（[VroidExportService.py](https://github.com/miu200521358/vroid2pmx/blob/main/src/service/VroidExportService.py)）；照れ/涙 用"复制脸材质 → 透過度 0 → 加算 1"放「その他」（[もにゃ note](https://note.com/monyanote/n/n77b5cf08c778)）。对 XPS 模型推荐：① 始终生成核心集占位（あ い う え お ん、まばたき 笑い ウィンク ウィンク右 ウィンク２ ｳｨﾝｸ２右 じと目 びっくり、真面目 困る にこり 怒り 上 下、照れ 涙），英文名取 Cats 词典（あ→Ah、まばたき→Blink、笑い→Blink Happy、真面目→Serious、困る→Sadness、照れ→Blush 等）（[Cats dictionary.json](https://github.com/absolute-quantum/cats-blender-plugin/blob/master/resources/dictionary.json)）；② 识别到下颌/眼皮/眉骨时按 vroid2pmx 结构生成 ボーンモーフ（面板 0）并用 群モーフ 对外暴露标准名；③ XPS 可选表情网格（`FAU|happy` 类）转 材質モーフ；④ 顶点表情雕刻留给人工，但提供 `mmd_tools.apply_bone_morph`（当前姿势写入骨骼モーフ）与 `convert_bone_morph_to_vertex_morph`（烘成顶点モーフ）两个现成算子（[mmd_tools operators/morph.py](https://github.com/MMD-Blender/blender_mmd_tools/tree/main/mmd_tools/operators)）。在 mmd_tools 中登记只需形态键名 = 日文名，`vertex_morphs.add()` 填 `name/name_e/category`，再 `DisplayItemQuickSetup.load_facial_items` 加入「表情」枠；导出前所有形态键 `value=0`。

### 物理：XPS 没有刚体，默认只建身体碰撞体，发裙链作为带预设的可选项

"XPS physics is configured manually"、XPS 模型不含刚体（[DanceXR concepts](https://vrstormlab.com/dancexr/concepts)）。Blender 侧 mmd_tools 只提供"对选中骨逐个加刚体 / 对父子刚体对加 Joint"：`mmd_tools.rigid_body_add` 默认 `size=[0.6,0.6,0.6]`（乘骨长）、mass 1、friction 0.5、bounce 0、linear_damping 0.04、angular_damping 0.1、collision group 1，刚体放骨中点并随骨朝向；`mmd_tools.joint_add` 默认角度限制 ±π/4、线性限制 0、弹簧 0（[mmd_tools operators/rigid_body.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/rigid_body.py)）；MMD Tools Append 没有发链/裙链生成器，只有"刚体→布料"与胸部 Pyramid 布料（[blender_mmd_tools_append](https://github.com/MMD-Blender/blender_mmd_tools_append)）。真正的参数经验来自 PMXE 生态。KKPMX 硬编码：链式刚体有子骨→胶囊，半径 0.2×骨长、位于骨中点，链首 `phys_mode=0`（static，"to avoid fluid"），move_damp 0.999 / rot_damp 0.9999；链式 Joint 旋转限制 ±10°/±5°/±10°，movespring [500,100,20]、rotspring [250,50,10]；身体碰撞体 damp 0.9999；裙子 7 条×5 段、箱宽 0.6、厚 0.02；碰撞组 BODY=1、ARMS=2、DEFHAIR=3、SKIRT=4、CHEST=8…（[kkpmx_rigging.py](https://github.com/CazzoPMX/KKPMX/blob/master/src/kkpmx_rigging.py)）。vroid2pmx 的身体碰撞体：下半身 胶囊 ratio 0.8/0.4/1、上半身 1/0.5/1、首 0.6/0.7/1、頭 球 0.6，全部 ボーン追従、mass 10、damp 0.5/0.5、repel 0、friction 0，并明示「物理は当ツールでは設定していないので、PmxTailorで設定してください」（[VroidExportService.py](https://github.com/miu200521358/vroid2pmx/blob/main/src/service/VroidExportService.py)）。PmxTailor 的预设与公式最系统：質量/空気抵抗/形状維持 三滑杆（默认 1.5/1.8/1.5），髪(ショート) 2/4.5/1.6、髪(ロング) 2.5/3.8/1.6、布(コットン) 3.2/1.5/1.5、胸(小) 4.0/1.5/3.0；派生 移動/回転減衰 = clamp(1 − (1 − 空気抵抗/5)·(質量/10)·1.2, 0, 0.9999)（髪 ×1.2、胸 ×3），摩擦 = 空気抵抗/5 × 0.7，Joint 基准限角 89°·(1 − 空気抵抗/5)，縦/横/斜 比例 0.9/0.8/1，回転バネ 系数 縦 40/30、横 30/20、斜 20/10（[pmx_tailor ParamPanel.py](https://github.com/miu200521358/pmx_tailor/blob/main/src/form/panel/ParamPanel.py)）。头发教程口径：质量由根到梢递减（10 节示例 "40, 35, 30, 25, 20, 15, 10, 5, .5, 1"），移動減衰 "0.5555 at the top… down to 1" 不超 0.9，回転減衰 "0.999999999"，"You will never need repel or friction"（[Oomary's guide](https://learnmmd.com/http:/learnmmd.com/oomarys-guide-to-mastering-mmd-hair-physics/)）。崩坏主因是刚体初始重叠（"when two bodies are initialized while touching, you get insane amounts of jiggle"）（[LearnMMD skirt presets](https://learnmmd.com/http:/learnmmd.com/pmxe-skirt-plugin-presets-skirt-tips/)）与孤儿 Joint——Joint 引用的刚体索引为 −1 直接导致 MMD 崩溃（[model_overall_cleanup.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/scripts_for_gui/model_overall_cleanup.py)）。**推荐默认**：只生成身体碰撞体（頭/首/上半身/上半身2/下半身/腕/ひじ/足/ひざ 的 ボーン追従 球/胶囊，group 1，damp 0.99+，repel 0）；对识别出的头发/尾巴/裙链提供"髪 / スカート / 単一揺れ物"三档预设（KKPMX 常量为缺省，PmxTailor 公式为进阶），默认关闭、由用户勾选；用 `FnRigidBody.new_rigid_body_object + setup_rigid_body_object`、`new_joint_object + setup_joint_object` 构造并以 `MoveObject.set_index` 控制顺序；校验 Joint rb ≠ −1、ボーン追従 刚体必有骨、链首与身体碰撞体不重叠。

### 校验：按 PMXEditor 49 项与 Nuthouse01 顺序自检，崩溃级错误阻断导出

PMXEditor「PMXデータの状態検証」是发布前的硬门槛，10 类共 49 项：System（追加 UV >4）、Model Information（无名/无注释）、Vertexes（无效法线、无效权重、缺 SDEF 值、孤立顶点）、Faces（引用不存在顶点、非法面、重复面）、Materials（无名、重名、零面材质、贴图/sphere/toon 文件不存在、sphere 已命名但禁用）、Bones（骨数过多、无名、重名、循环引用、"Incorrect order of bones"、父/子/表示先/付与親/IK 引用无效）、Morphs（无名、重名、偏移引用越界）、Display panel（枠无名/重名、骨/モーフ未注册或重复注册、引用无效、"Root and/or Expressions (System) Display Panel Groups… do not exist"）、Rigid bodies、Joints（无名、重名、刚体 A/B 不存在）（[PMX error checker quick reference](https://github.com/powroupi/blender_mmd_tools/wiki/PMX-error-checker-quick-reference)）。Nuthouse01 的 `model_overall_cleanup` 给出可编程的修复顺序：`uniquify_names`（重名追加 `*2`）→ `prune_unused_vertices` → `prune_invalid_faces` → `prune_unused_bones` → `weight_cleanup`（EPSILON=0.00001 以下丢弃、归一化、按组数降级 BDEF4→BDEF2→BDEF1）→ `dispframe_fix` → `bonedeform_fix`（通过提高变形层保证骨在父/付与親/IK 目标之后变形，1000 次不收敛判循环）→ `alphamorph_correct` → `morph_winnow`（顶点位移 <0.0003 删除）→ `translate_to_english`，附加 `find_crashing_joints`、`find_boneless_bonebodies`、`find_toolong_bonemorph`（>15 字节）、`find_shiftjis_unsupported_names`、`find_shadowy_materials`（alpha 0 但边线开）（[model_overall_cleanup.py](https://github.com/Nuthouse01/PMX-VMD-Scripting-Tools/blob/master/mmd_scripting/scripts_for_gui/model_overall_cleanup.py)）。mmd_tools 4.5 的 Model Debug 面板提供 `mmd_tools.validate_bones / validate_morphs / validate_textures`（cp932 可编码、≤15 字节、重名、贴图缺失/同路径异名/同名异路径）与 `fix_bone_issues / fix_morph_issues / fix_texture_issues`（OpenCC s2t→t2jp 转写、截断到 13/14 字节加后缀、缺失 toon 回退共享 toon），结果写入 `Scene.mmd_validation_results`（[mmd_tools model_validation.py](https://github.com/MMD-Blender/blender_mmd_tools/blob/main/mmd_tools/operators/model_validation.py)）。格式层面只写 **PMX 2.0**：2.1 的 QDEF/SoftBody/非标准 Joint 会触发 MMD「PMXファイルのバージョンは2.0しか読み込めません」（[VPVP wiki PMXの概要](https://w.atwiki.jp/vpvpwiki/pages/284.html)；[たるっこ](http://tarucco2.blog.shinobi.jp/atelier/pmx%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB%E3%83%90%E3%83%BC%E3%82%B8%E3%83%A7%E3%83%B3%E3%81%AE%E7%BD%A0)）。推荐把 Nuthouse01 的规则移植为插件内部实现（其工具 2022 年起停更），把 mmd_tools 的 `validate_*` 作为第二道门，并把"Joint 引用 −1、面板 0 モーフ进表示枠、表示枠モーフ ≥256、顶点モーフ引用越界、骨/IK 引用无效"列为**阻断导出**的崩溃级错误，其余（重名、超长名、零面材质、孤立顶点、alpha 0 开边线）自动修复或警告。

风险与未知项，按对设计的影响排序：**(1) XPS 单位与典型身高无文档且本机无任何 `.mesh/.ascii/.xps` 样本**，缩放与 A 姿势检测都需要真实模型回归；**(2) `hasBoneDirections`（flag 7）为真时文件是否多出骨骼方向数据、放在何处，没有任何实现读取它**，Daemon 变体 ASCII 还带骨骼旋转/轴，自写读取器需对骨骼块里的额外数值行容错（[Tosyk ASCII-Plugins](https://github.com/Tosyk/ASCII-Plugins/blob/main/README.md)）；**(3) TDA 式等常见模型的实际臂角未测得**，ローカル軸 的左右 Z 符号约定无一手文档；**(4) そぼろ 原版闭源**，移植版自述「ほぼ同じ」但权重算法细节未必逐字相同；**(5) Riveda 的 46 个面部骨名只拿到首尾两项**，「64 根标准骨」的精确清单（まめピカ xlsx）未取得；**(6) mmd_tools 没有公共 API 稳定性声明**，MMD Tools Append 是唯一第三方调用范例，Blender 5.0 下 `pose_bone.hide` 与 `bpy.ops.rigidbody.constraint_add` 在 `temp_override` 中的行为未验证；**(7) 自动权重（bone heat）在游戏模型的多层相交壳体上会 "Overlaps can occur"，且会覆盖同名已有组**（[Blender Manual Armature Deform](https://docs.blender.org/manual/en/latest/animation/armatures/skinning/parenting.html)），只能对单独分离的缺权重部件局部使用；SDEF 的 `C/R0/R1` 无公开生成算法，默认只输出 BDEF；**(8) MMD 的顶点/面/骨数硬上限无权威来源**（PMXE 自己写 "How many bones is too many? Sorry, I don't know."）；**(9) 再分发规范在英文与中文社区方向相反**（Riveda 反对给转换品加限制，模之屋默认"禁止二配、禁止商用"），插件应中立，但建议导出时自动把来源/提取者/转换者写入模型注释（[aplaybox 规约](https://www.aplaybox.com/article/details/695739136)；[Riveda 2018](https://www.deviantart.com/riveda1972/journal/MMD-XNA-Game-ripped-models-748793671)）。

## 需要项目负责人拍板的决策点

以下每项给出选项与本报告的推荐；"推荐"基于前文证据，但最终取舍涉及工期与定位。

1. **XPS 读取：内嵌读取器 vs 依赖 XPS Tools 分支。** 推荐**内嵌**。格式只有两个布尔分支（切线、变长权重），自写几百行即可覆盖 `.mesh`/`.xps`（2.x/3.x）/`.mesh.ascii`/`.pose`，并保留 `uvLayerId`、flags、默认姿势与 `+`/`-`/`|`；上游无许可、本机 2.0.2 已坏、mayloglog 分支只支持 5.0+、Valerie 分支无 LICENSE。备选：若决定只支持 Blender 5.0+ 且接受 GPL，可依赖 mayloglog 的 "XPS Import/Export"。
2. **PMX 写出：mmd_tools vs 自写写出器。** 推荐**以 mmd_tools ≥4.5 为运行时依赖**（动态导入、版本门槛、只传已知 kwargs），并保留直接构造 `pmx.Model` → `pmx.save` 的兜底路径。理由：它承担了 PMX 2.0 二进制、BDEF 选择、材质/刚体坐标换算、Bone Order、表示枠、校验与翻译，社区 60 万+ 安装量意味着用户环境本就有它。备选：完全自写（只在 mmd_tools API 失稳时启用兜底）。
3. **插件许可：** 推荐 **GPL-3.0-or-later**。这是 extensions.blender.org 的硬要求，也是 import mmd_tools 的合规选择，同时允许并入 MIT/LGPL/GPL-2+ 的词表与算法。
4. **目标 Blender 版本：** 推荐 **4.2 LTS 起**（与 mmd_tools v4.x 的 `blender_version_min = "4.2.0"` 一致），在 4.5 LTS 与 5.x 上测试，放弃 3.x。代码直接按 4.x API 写（骨骼集合、`normals_split_custom_set_from_vertices`、`NodeTree.interface`），并对 5.0 的 `pose_bone.hide` 等差异做分支。
5. **A 姿势策略：** 推荐**参数化**：上臂低于水平 θ₁ 默认 30°、前臂附加 θ₂ 默认 10°（あにまさ ver.2.3 实测 29.72°/40.28°），预设 "45°（Hogarth/通用）" 与 "37°（Convert-to-MMD）"；转换前自动测源臂角并在已接近时跳过；用矩阵法烘进网格与形态键。备选：固定 45°。
6. **缩放策略：** 推荐**默认按身高归一化**到目标 20 单位（可改），覆盖项为固定倍率（米制模型 12.5）。备选：固定 12.5（Convert_to_MMD5 做法）或 10（powroupi 教程）。
7. **骨骼映射数据格式：** 推荐**双层 JSON**：每模型 `{slot_id: bone_name}`（兼容 VRM Save/Load 与 Convert-to-MMD `CTMMD.json` 形状）+ 体系预设 `{slot_id: [alias...]}`（支持 `\L` 侧别通配、Cats/Rokoko 词表导入）+ 可选的 `BoneDict.txt` 导入/导出 + Rokoko 式用户修正学习表。内部槽位 = VRM/Unity 55 骨 + MMD 控制骨槽，带 `requirement / parent_requirement / 固定父骨`。备选：mmd_tools_helper 式多列 CSV（可读性好但表达不了父骨回落）。
8. **`spine lower` 归属：** 推荐默认 `pelvis → 下半身`、`spine lower → 上半身`、`spine upper → 上半身2`（Riveda/Hogarth/Model-To-PMX 多数派）；`pelvis` 缺失且 `root hips` 带权重时自动回落为 `root hips → 下半身` 并新造无权重 センター，UI 把 `下半身` 槽标"需确认"。Convert-to-MMD 的 `spine lower → 下半身` 作为可切换的预设变体保留。
9. **缺失骨补全范围与 IK 口径：** 推荐分三档。**Tier 1 始终生成**：全ての親、センター、グルーブ、首（缺时）、両目（+左目/右目 付与 1.0）、つま先（缺时）、左右 足ＩＫ/つま先ＩＫ（loop 40/3、单位角 2.0/4.0 rad、膝 X −180°～−0.5°、無 手臂 IK），`親指０` 在 XPS 有 `finger 1a` 时直接映射。**Tier 2 默认开启**（对应 ssb 默认勾选）：上半身2（缺 `spine upper` 时按 0.35 生成并分割权重）、腕捩/手捩 + 捩1/2/3（0.6 位置、0.25/0.5/0.75 付与）、腰 + 腰キャンセル、足IK親、肩P/肩C、左右ダミー、操作中心。**Tier 3 默认关闭**：足D/ひざD/足首D + 足先EX（权重与刚体整体迁移、変形階層 +1，Blender 侧还要生成影子骨约束，复杂度高，验证后再默认打开）。
10. **XPS twist 骨处理：** 推荐**先并回父骨（Cats `bone_reweigth_to_parent` 列表 + Riveda 建议），再按 ssb 公式重建 腕捩/手捩 并重新分配权重**；腿部 twist 一律并回（Hogarth/Append 的经验）。备选：把 XPS 多段 twist 直接重映射到 腕捩1/2/3（Cats `fix_twist_bones` 的 25/50/75% 比例可借用），保留原蒙皮但层级需手工核对。
11. **表情自动化程度：** 推荐**占位核心集（あにまさ 30 + え）始终生成 + 识别到面部骨时生成 ボーンモーフ/群モーフ + XPS 可选网格转 材質モーフ**；顶点表情留人工并提供 mmd_tools 的 `apply_bone_morph` / `convert_bone_morph_to_vertex_morph` 入口。备选：只生成占位（最省）或完全不生成（留给 PMXE）。
12. **物理自动化程度：** 推荐**身体碰撞体默认开、发/裙链生成默认关但带三档预设**（KKPMX 常量为缺省：胶囊半径 0.2×骨长、首节 static、damp 0.999/0.9999、Joint ±10/±5/±10°、rotspring [250,50,10]；进阶用 PmxTailor 公式）。备选：全部留给 PmxTailor / 曲面自動設定（日本社区现状）。
13. **校验严格度：** 推荐**崩溃级错误阻断导出**（Joint 引用 −1、面板 0 モーフ进表示枠、表示枠モーフ ≥256、顶点モーフ引用越界、骨/IK 引用无效、PMX 2.1 特性），其余自动修复或警告；可选内置"载入标准 VMD 比较标准骨朝向偏差"的回归测试。备选：只跑 mmd_tools `validate_*`。
14. **贴图处理：** 推荐**默认复制到 `textures/`、转 PNG、ASCII 重命名、cp932 预检，非 diffuse 贴图写入材质 comment**；"lightmap 预乘进 diffuse"与"DDS 原样保留"作为选项。备选：只改路径不复制（mmd_tools `copy_textures_mode=NONE`）。

## 结论

把这七份调研放在一起看，XPS→PMX 的难点从来不在格式转换——XPS 读取器与 PMX 写出都是小而确定的工程——而在于**MMD 把"动作可复用"的全部前提（日文名、A 姿势、层级、腿 IK、身高）都隐含在模型里**，而游戏模型恰好在每一项上都不满足。社区十年的手工链路本质上是在人工补这些隐含前提，现有自动化工具各自只补了其中几项。本方案的真正增量是三件事：把隐含前提显式化为带实测默认值的参数（30°/40° 臂角、20 单位身高、0.6 捩骨位、40/3 IK loop）而不是写死常数；把"识别→补全→校验"做成围绕中间人形模型的幂等阶段，使每一步的自动结果都可被逐槽修正并重跑；以及用 VMD 回归代替"套一支極楽浄土看看"的经验式验收。

这也意味着插件的定位可以比"XPS 转换器"更宽：XPS 读取器只是最薄的一层，中间人形模型、三级匹配、ssb 公式补骨、mmd_tools 契约封装对任何游戏拆包骨架都适用，Convert-to-MMD 的 24 套预设与 Cats 的别名词表已经说明了这一点。短期内 PMXEditor 仍是顶点表情雕刻与精细物理的最终装配台，但如果 Tier 1/2 补骨、材质默认值与校验门禁都在 Blender 内自动完成，留给 PE 的就只剩创作性工作，而不是今天教程里那六集"改名、合并、IK、表情、物理、材质修正"。
