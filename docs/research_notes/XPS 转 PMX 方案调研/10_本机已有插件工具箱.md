## 0. 总览

### Takeaway
1. **完整 XPS→PMX 管线的零件，本机大多已经有了，而且多数经过批量验证**：owner 的 ROE 管线（`roe_pmx_tools` + 批处理 worker，150 个模型跑通）提供阶段框架、骨架预处理、胸部物理、验证门禁与导出；`Convert_to_MMD5` 提供骨骼识别 / 补全 / IK / 付与 / 权重规则 / 身体碰撞体 / 发链，以及最新的表情引擎；`mmd_cloth_physics` 提供衣物物理；三个 `*_game_materials` 提供“导入 PMX 后回挂高清材质”的切换机制。新插件的主要工作是**整合 + XPS 适配 + CSV 映射与检查器 + 导入时采集材质清单**，而不是从零写算法。
2. **上一次通用尝试（`xps_to_pmx` / `C2M/`）不能复用**：它的 Stage 0–5 没有一个在真实模型上可用，预设 JSON 连反序列化都会失败（本次实测）；但它“为什么变乱”（1b.5 的 12 条）正好是新插件的架构约束清单。
3. **需要 owner 拍板的几处约定**：胸骨默认名（`左乳奶/右乳奶` 还是 `左胸/右胸`）、碰撞组 15 的用途、脊柱插骨策略（新插 上半身1 还是 上半身3）、XNA Lara `spine lower` 映射到 上半身 还是 下半身、A-pose 角度（37° 还是 36°）。详见 10.4。

## 1. `xps_to_pmx`（安装副本，v1.0.0，2026-03-29）——上一次“通用 XPS→PMX”尝试的插件本体

### Takeaway
`ADDONS/xps_to_pmx/` 是 `C2M/xps_to_pmx/` 子包的同步副本（缺最后一次提交加的“缺失骨骼检测”面板）。它搭好了两个 N 面板页签、一套 dataclass 数据模型、49 根骨的“MMD 标准骨架” JSON 和 Stage 0–5 六个操作符，但**没有一个 Stage 在真实模型上产出过可用结果**：自动映射因为预设 JSON 反序列化必然失败而退化成“每根骨映射到它自己”；Stage 1 把缺失骨放在占位坐标；Stage 2 的 A-pose 实际不生效；Stage 3 只有 FK→D 能跑；Stage 4 的付与写在了 `FnBone` 包装对象上（空操作）；Stage 5 因为没有 mmd_tools 根对象而导出失败、转而另存 .blend。**判定：REPLACE**——只保留“逐骨映射记录 + 来源/备注/置信度”“以 MMD 标准骨为主干的树形检查视图”“check/fix 注册表”三个思路，代码不复用。

### Cited Findings

**基本信息与安装副本差异**
- `bl_info`：`"name": "XPS to PMX"`，`"author": "Claude"`，`"version": (1, 0, 0)`，`"blender": (3, 0, 0)`，`"location": "View3D > Sidebar > XPS to PMX"`，自定义键 `"last_updated": "2026-03-29 20:30:00"`（用来判断 Blender 加载的是不是新代码）— `ADDONS/xps_to_pmx/__init__.py:12-25`

#### 1b.5 为什么变“乱”：从代码能看到的 12 个架构问题

1. **一个仓库、两个插件、三条管线、两套映射数据模型**：顶层旧插件（12 步 + 25 个“槽属性名 → 源骨名”扁平预设）；`xps_to_pmx` 的 `ui.py` 管线（`pipeline.stage_*` 包装 + 旧权重函数）；`xps_to_pmx` 的 Mapper 页签（树面板上的 Stage 0–5 按钮直接调操作符）。新模型（XPS 名 → `BoneMapping`）与旧预设互不兼容，旧插件已验证的预设和算法都没接过来。
2. **“真理源”有四份且互相矛盾**：被遮蔽的 `mapping.py`；缺手指/つま先/上半身3、含非标准骨、层级有错的 `mmd_standard_skeleton.json`；每个 Stage 自己硬编码的骨名表（`stage_3` 分区集合、`stage_4` 付与/IK/骨组、`weights.py` 的 `transfer_map`）；未被引用的 `bone_checks.py`。同一根骨在不同文件里写法不同——`左足IK親`/`左足ＩＫ親`、`足D.L`/`左足D`、`肩P.L`/`左肩P`、`つま先.L`/`左つま先`、`腕捩.L`/`左腕捩`——字典查找静默落空。
3. **状态放在模块级全局变量**：`_GLOBAL_CONFIG`（`mapping_ui.py:18-21`）、`_TREE_STATE`（`mmd_bone_tree_ui.py:22-29`）不进 .blend、不随 Undo、重载插件即丢、多个骨架共用一份；另有 6 个 Scene 字符串属性存 JSON（`__init__.py:35-73`）。Stage 操作符 `from .. import mapping_ui` 直接读 UI 模块的全局，执行层反过来依赖 UI 层。
4. **失败被吞掉、成功被谎报**：包装函数忽略 `bpy.ops` 返回值（`pipeline.py:187-264`）；大量 `except Exception`；HipBlend 找不到骨就 `continue`；`FnBone` 赋值无效却计数 +1；Stage 5 失败时另存 .blend 并报“模型已准备”；树面板写死“✅ 完整转换流程已实现！”。
5. **Schema 漂移没有校验**：预设升到 v3.0 加了 `zone` 等字段，`cls(**data)` 必然 TypeError（本次实测）；外层 try/except 把这个错误变成“自动映射静默退化为恒等映射”；规则类型字符串与代码枚举不一致；`C2M/fix_preset_schema.py` 只补字段不删字段。
6. **检查是同义反复**：`parent_mmd` 本身就是由 XPS 父骨的映射推出来的（`detection.py:379-401`），再拿同样推导出的“期望父级”去比，永远相等——本次构造“上半身 挂在 下半身 下”的错误层级，`validate_parent_relationships()` 判为通过；`parent_mmd_expected` 自动映射时从不填写；`vertex_group_count` 从不计算，权重百分比 = `vertex_group_count × 0.1`。
7. **自动映射算法选错**：只用字符串相似度对 29 个 DAZ 风格名，无拒绝阈值、无一对一、无层级/位置/侧别约束；文档里“手指映射到 センター、需要手工改”的场景，正是这个算法的必然产物。
8. **文档先于代码且夸大**：同一天 17 份文档、约 7.6k 行；“✅ 100% 完成”“系统已完全可用”“生产级别 - 已测试序列化”；示例输出是编的；设计稿要求 Blender 面板做不到的东西（行内配色、hover、动画、虚拟滚动、响应式两栏）。
9. **没有可自动运行的测试**：`C2M/CLAUDE.md` 明写 “There are no unit tests”；`test_mapping_system.py` 是要在 Blender 里手动运行的打印脚本，没有一个断言。而 `data_structures` / `detection` 的大部分逻辑不依赖 bpy，本可离线测试——本次两段 Python 就暴露了反序列化失败和校验失效。
10. **开发循环靠“复制 + 时间戳”**：8 个同步/清缓存/改时间戳脚本 + `bl_info["last_updated"]`，只为判断 Blender 到底加载了哪份代码；`sync.py` 每次删掉整个安装目录，而“保存预设”恰好写在安装目录里，用户数据会被同步删除。对照：ripper_tpose 系列用目录联接 + `importlib.reload`（见第 2、4 节）。
11. **先铺满再验证**：一天内一 Stage 一提交铺完 0–5，没有任何一个 Stage 在真实模型上跑通后再做下一个；同仓库已验证的旧算法（0.46 / 0.6 / 钟形填充 / 快照监控）没有复用，新 `weights.py` 另写了一套不同且有 bug 的实现（用 Z 判左右、骨名拼接错误）。
12. **没有分层**：操作符里混着业务逻辑、print 日志、UI 状态和文件 IO；没有“纯 Python 领域层 / Blender 适配层 / UI 层”的边界，也没有“只读分析 → 可审阅计划 → 执行 → 只读自检”的阶段边界。xps_to_mmd-main 的 `doc/architecture_retrospective.md` 事后总结了同样的教训（见 10a §3.10）。

## 2. `roe_pmx_tools`（v0.1.0）——最接近的前身：四个可检查的阶段

### Takeaway
`roe_pmx_tools` 只有一个 20 KB 的 `__init__.py`，是批处理 worker `RT/scripts/riseoferos/export_character_model_blender.py`（2569 行，下称 `W`）外面的一层薄 UI：四个按钮调用的正是批处理无头运行时的同一批函数、同样的顺序，所以“手动导出和批量导出同一个 FBX 得到的是同一个文件”。它串起了 `roe_xps_addon`（导入与材质）、`Convert_to_MMD5`（骨架转换与身体碰撞体）、`mmd_face_morphs`（骨骼表情）、`mmd_cloth_physics`（布料/头发）、自己的胸部物理，以及 mmd_tools（刚体、付与、表情登记、导出、回读校验），每一阶段把结果写进面板和 PMX 旁的 `*.report.json`。这套流程已在 124 个 ROE 主模型和 26 个套装/裸模上批量跑通（`RT/docs/roe-hq-materials.md` §4）。**判定：ABSORB**——架构（薄 UI + 共用 worker + `_state` 交接 + 阶段报告 + 验证门禁）与 worker 中的大部分通用函数直接移植；ROE 专用部分（Biped 槽位表、对 roe_xps_addon 的依赖、头部槽与眼球、HQ 贴图）改成“来源适配器”。

2. **贴图查找** `find_tex`（`:54-81`）：先精确 glob 再递归；接受游戏包里的拼写错误 `Abedo`；只在同一角色根目录下的 `_textures*` 兄弟目录里找；`find_family_tex` + `EYEBROW_TEXTURE_FAMILY = {'i': 'h', 'j': 'd'}`（`:89-107`）借用别的家族的共享头部贴图；多体型共享贴图时按体型字母 + 角色前缀精确匹配（`:1475-1492`）。
3. **头部五槽分类** `classify_head`（`:917-1183`，原理见 `RT/docs/face-eye-materials.md`）：AssetStudio 把头部子网格合并成一个无槽网格 → 用“连通块 + 骨权重类别（Eyeball / Eyebrow / Eyelid / AC eyelid_bone）+ UV 象限约定（脸部皮肤在 u∈[1,2]）+ 原始材质名”还原 → 槽 0 脸、1 眼球、2 睫毛、3 眉毛、4 透明罩；只改 `material_index`，不切几何（可逆、无损）。
4. **材质配方与常数**（`:35-41`；`albedo_mat` `:625-642`、`eye_mat` `:842-867`、`stroke_mat` `:870-895`、`transparent_mat` `:898-912`）：

| 常数/规则 | 值 | 用途 |
|---|---|---|
| `SKIN_DESAT` | 0.85（HueSat 饱和度） | 皮肤防偏粉 |
| `IRIS_CENTER` / `IRIS_R_IN` / `IRIS_R_OUT` | (0.5, 0.49) / 0.235 / 0.285（MapRange SMOOTHSTEP 1→0 作为眼白/虹膜混合因子） | 程序化眼白 + 中心虹膜圆盘（虹膜贴图外圈也是棕色，整张贴会没有眼白） |
| `SCLERA` | (0.90, 0.88, 0.87, 1)；眼球粗糙度 0.15、OPAQUE | 眼白 |
| `LASH_ALPHA_GAIN` / `LASH_DARKEN` | 1.5（钳制乘法）/ 0.55（HueSat 明度） | 睫毛（HQ 流程里会换成游戏眉毛着色器的“颜色×α”贴图） |
| 眉/睫笔触 | 粗糙度 0.6、高光 0.1、BLEND、不投影；**笔触形状在 alpha 通道** | — |
| 身体 / 丝袜 | CLIP / HASHED | 半透明衣物用 CLIP 会被裁没 |
| 透明罩 | **只用 Transparent BSDF**；Principled α=0 在 EEVEE 仍有高光月牙 | 隐藏层 |
5. **XPS 导出**（`export_xps`）：依赖 XNALaraMesh 的 `bpy.ops.xps_tools.export_model`；在临时副本上操作，场景不变；头部按槽拆成 face/eye/lash/brow，透明罩丢弃；网格名 `<renderGroup>_<名字>_<高光>`，名字里的 `_` 改成 `-`（XPS 用 `_` 作分隔符）；RG 5 = 仅 diffuse 无 alpha（脸/眼球/不透明身体），RG 7 = 仅 diffuse 带 alpha（睫毛/眉毛/头发/G09 翅膀）；带 HQ 贴图时升为 RG 24 / 25（diffuse + lightmap + bump + specular），高光 0.1 → 0.4（`hq_render_group` `:600-602`、`roe_xps_render_group` `:605-622`）；材质必须是名字恰为 `XPS Shader` 的组节点，优先用 XNALaraMesh 自己的 `material_creator.xps_shader_group()` 创建（输入 Diffuse、Lightmap、Specular、Emission、Bump Map、Bump Mask、MicroBump 1、MicroBump 2、Environment、Alpha —— `ADDONS/XNALaraMesh-master/material_creator.py:527-555`），残缺组改名让位；程序化眼球先烘成 `roe_eye_baked.png`；无贴图材质写 4×4 纯色图。
6. **HQ → XPS 贴图**（`RT/docs/roe-hq-materials.md` §3）：XPS diffuse = albedo × `_BaseColor`（线性空间相乘）、lightmap = AO、bump = 法线且**绿通道翻转**（XPS 文件头默认切线空间标志是反 Y）、specular = √(光滑度 × `_Smoothness`)（头发 0.35）。

**骨架方向修正** `roe.fix_xps_armature`（`:2454-2489`）：对每个骨架，若 `max|head.y| > 2 × max|head.z|` 且 ≥0.3，判为“躺平”（XPS 是 Y-up，XNALaraMesh 导回 .mesh 时网格转成 Z-up、骨架保留 Y-up）→ 子物体临时解除父子并保持世界矩阵 → 骨架 +90° X → `transform_apply(rotation=True)` → 挂回并重设 `matrix_parent_inverse`。新插件导入 XPS 后应把它做成一条“轴向一致性”检查，而不是默认执行。

**`roe.diagnose_model` 的检查项**（`:1809-1870`）：网格无面 / 无 UV / 无材质；面的材质索引超出槽数；空槽；无贴图（纯色）材质计数；关联骨架多于 1 个；可见网格按去掉 `.NNN` 后的名字重复；ROE 模式下需要从原 FBX 恢复槽布局的网格。结果写入 `diagnostic_report`，面板按“；”分行显示前 4 条。

**已知限制**（`RT/docs/xps-addon.md`「局限」）：皮肤降饱和、睫毛加深等 EEVEE 节点效果带不进 XPS；眼部透明罩不导出；单文件插件更新后必须重启 Blender。

## 4. `roe_game_materials` / `stellarblade_game_materials` / `vindictus_game_materials`——导入 PMX 后回挂游戏原始高清材质

### Takeaway
三个插件形状完全相同：MMD 页签里一个面板，按钮「换上游戏原始材质」，「游戏材质 / MMD 着色」切换，实时滑块（1.0 = 游戏原值），「参数恢复默认」「去掉游戏材质」（后两个插件还有「重新扫描存档」）；真正的工作都在 `RT/scripts/<游戏>/` 的核心模块里。三者都把高清网络**加进 PMX 原有的材质里**——一套带前缀的节点 + 自己的 Material Output，切换时只改哪个 Output 处于激活状态和混合设置，mmd_tools 的节点一个不删，所以再导出 PMX 结果不变（剑星实测 17 个材质一致，Reika A 两种状态导出逐字节相同）。三者的差别只在“怎样找到这个材质对应的游戏材质”：ROE 按颜色贴图 + 从 Unity 包读出的材质数据，剑星按材质名在 `*_HQ.blend` 存档里找，Vindictus 解析 Blender2XPS 导出名后在存档 .blend 里找。**判定：CALL**（三个插件依赖各自游戏的数据源，继续独立存在）；**ABSORB**：共同骨架（找模型、复制网络、增益节点、模式切换、设置 JSON、材质表情隐藏层、索引缓存、长度换算）收进新插件的“高清材质回挂”阶段，由 XPS 导入时采集的材质清单驱动（见本节末）。

**切换与调节机制（三者共用）**
- 自己的 Output 节点（带前缀名）；切换时设置各 Output 的 `is_active_output`（ROE `set_active_output` `:848-853`、`set_mode` `:855-871`；剑星 `set_mode` `:517-532`；Vindictus `set_mode` `:507-523`）。mmd_tools 的节点一直连着，所以在 mmd_tools 里改 MMD 材质时它不会把输出抢回去；导出读的 `mmd_base_tex` 原封不动。
- 每种模式一份材质设置（`blend_method, shadow_method, alpha_threshold, use_backface_culling, show_transparent_back`），以 JSON 存在材质上（剑星 `sbhq_game_settings` / `sbhq_mmd_settings`；Vindictus 存在 `vind_hq_base` 的 `game` / `mmd` 键里）。
- 实时滑块：在已连线的 Principled 输入前插 MULTIPLY 增益节点（剑星 `insert_gain` `:242-256`、Vindictus `_gain` `:304`）；常数输入记下原值后原地相乘；法线强度、发光强度的原值记在节点上。
- 复制网络（剑星/Vindictus）：从存档追加游戏材质 → `copy_network` 按 `bl_rna` 属性逐个复制节点、复制颜色渐变与输入默认值、按 socket identifier 重连（剑星 `:190-239`、Vindictus `:235-295`）→ 删掉追加进来的那份和空库条目（用户自己链接的库保留）。
- 材质表情隐藏的层（剑星 0.2 / Vindictus）：游戏 alpha × MMD alpha（接 mmd_tools 表情绑定后的 alpha 来源）；隐藏时改 BLEND、显示背面、不投影、SSS 置 0，避免 EEVEE 在层交界画黑线；剑星用 `depsgraph_update_post` + `frame_change_pre` 两个处理函数按表情滑块算当前透明度（`stellarblade_game_materials/__init__.py:77-99, 283-306`）。

**PMX 侧能带多少**：PMX 只有一张颜色贴图。ROE 的 `use_pmx_textures` 把颜色贴图换成预先算好的 `<缓存>\export\<名>__pmx_diffuse.png` = albedo × `_BaseColor` × AO（`hq_materials_blender.py:1017-1029`）；剑星导出时把 AO 乘进颜色，并把亮的部分拆成 `<材质>_gloss`、用 sphere 贴图加高光。法线、金属度、粗糙度只能在 Blender 里回挂——这正是 owner 要的“导入 PMX 后挂高清材质”。

**通用化：一个由导入时数据驱动的“高清材质回挂”阶段**
1. **导入 XPS 时采集材质清单**：XNALaraMesh 导入后每个材质是一个 `XPS Shader` 组节点（输入 Diffuse / Lightmap / Specular / Emission / Bump Map / Bump Mask / MicroBump 1 / MicroBump 2 / Environment / Alpha），按输入插口读出贴图与参数，写一份 sidecar JSON（如 `<模型>.materials.json`，与 PMX 同目录）：材质键、原 XPS 网格名与材质名、render group 与参数、各角色贴图的绝对路径（diffuse / lightmap(AO) / bump（记录绿通道约定）/ specular / emission / bump mask / microbump1/2 及平铺 / environment）、alpha 方式、UV 层名、原始尺寸（供 SSS 等长度换算）。
2. **导出 PMX 时把材质键写进 `mmd_material.comment`**（剑星 `layer=…; source=…` 的先例），这样改名、拆分（`_gloss`）、爆衣副本（`_burst` / `_nude`）之后仍能找回。
3. **导入 PMX 后**：按 comment 键 → 材质名 → 颜色贴图名的顺序匹配清单条目；在原材质里建 `xhq_` 前缀网络 + 自己的 Output；沿用 `set_mode / apply_params / remove` 和“每种模式一份设置 JSON”的约定；材质表情隐藏层沿用剑星/Vindictus 的 alpha 相乘 + 处理函数方案。
4. **配方按“材质角色”写，而不是按游戏写**：pbr / skin / hair / eye / stroke（眉睫）/ glass，每种角色定义贴图通道布局（XPS render group 语义、Unity MGAC、UE ORM/ARM）与默认参数；ROE / 剑星 / Vindictus 的核心模块可以作为“配方提供者 + 数据源”继续存在（CALL）。

## 8. 与流程重叠的其他插件：Tpose_change / mmd_tools_helper / mmd_uuunyaa_tools（摘要，详见 10b Part B）

**`Tpose_change`**（ble_work，0.2.1，2026-07-11；`ADDONS/Tpose_change/`）：把**无骨骼**、任意姿势的人形网格（游戏提取件、扫描件，可分多个部件）变成带骨架和权重、可烘成 T/A 姿势的模型。AI 引擎在独立的 Python 3.11 + torch 子进程里跑 Make-It-Animatable（CVPR 2025），生成 Mixamo 52 骨，结果要过“T 形绝对检验”，不过关降级为几何引擎（沿高度分层估关节 + 体素测地蒙皮 + 逐骨 aim，19 骨模板）。XPS 本来就有骨架和权重，所以与新插件重叠的只有三块：`pose.py`（按语义角色摆 A/T：A = 手臂 38°、腿外张 4°；T = 手臂 82°；抬臂时锁骨分担 25%）、`bake.py`（Mysteryem 算法，来自 Cats PR#438：逐个形态键钉住求值后写回再 `armature_apply`，正确处理静音键、带顶点组掩码的键和非 Armature 修改器，先全量捕获再统一写回；其 docstring 指出 Convert_to_MMD5 `align.py` 现行的形态键处理在旋转区域不对）、`qc.py`（手臂水平偏差 ≤12°、肘部残余弯曲 ≤15°、左右镜像最近邻误差 ≤3% 身高、拉伸破面边（比值 >2.5）≤0.5%、边应变均值 ≤5% 且 >50% 的边 ≤1%）。操作符：`tpose.run_full / run_mia / run_geo / geo_build / geo_skin / geo_pose / bake_rest / qc / normalize_pose / bake_finish / rebind_weights` 等。**判定：CALL**（MIA 环境太重，作可选外部工具）**+ ABSORB `bake.py` / `pose.py` / `qc.py`**——新插件做 A-pose 修正时用 `bake.py` 保住已有形态键，`qc.py` 的阈值并入验证门禁。

### 10.4 延续 owner 习惯的约定
1. **阶段按钮**：带圈数字 ①②③④…，加「一键 ①→N」和「重来」；每一步之后都能在视口检查；面板底部报告框每步 2–3 行、末行写“下一步: …”；PMX 旁写 `<名>.report.json`。
2. **手动 = 批量**：核心逻辑放在能无头运行的模块里，UI 只调用它；批处理用 `blender -b --factory-startup --python <脚本> -- <参数>`。
3. **安装与开发循环**：仓库目录 + 目录联接到 addons；核心模块在阶段 ① 或 register 时 `importlib.reload`；用户数据（CSV、预设、报告、缓存）放在插件目录之外（先例：`%APPDATA%\Blender Foundation\Blender\3.6\config\` 下的索引 JSON、`E:\game_export\…` 存档）。
4. **面板位置**：新插件自己的页签负责“XPS → PMX”的各阶段；导入 PMX 之后才用的面板（高清材质、物理微调、表情微调）放 MMD 页签，与 ROE / 剑星 / Vindictus 游戏材质、Cloth Physics、Face Morphs 并列。
5. **输出**：默认输出目录不放进会被重新提取清空的源目录（先例 `D:\roe_exports\pmx_manual\<名>\<名>.pmx`）；`copy_textures=True`；米制模型导出缩放 12.5、导入 PMX 用 0.08。
6. **命名**：MMD 标准日文名（`ＩＫ` 全角、手指全角数字、`上半身2` 半角）；超过 15 字节 Shift-JIS 的骨名自动缩短、原名进 `name_e`；表情按 owner 的决定同时支持骨骼 morph 与顶点 morph——沿用 roe_pmx_tools 的 `pmx_morphs`（vertex / bone）枚举，并加上表情引擎的 AUTO（按 4 权重误差逐个选）；表情名以 10b 的并集表为准（`ｳｨﾝｸ２右` 与别名 `ウィンク２右` 都生成；ウィンク 闭模型自己的左眼）。
7. **物理默认**：胸 = owner 的乳奶模板；衣物 = mmd_cloth_physics 预设；头发 = Convert_to_MMD5 hair 参数；身体碰撞体 = `_BODY_DEFS`。
8. **文字风格**：中文界面文案、日文骨名原样；文档写在 `docs/`，只写已验证的行为并附数据（`RT/docs/` 的写法）。

**需要 owner 拍板的约定**：胸骨默认名（owner 模板的 `左乳奶/右乳奶` 还是 Convert_to_MMD5 的 `左胸/右胸`）；碰撞组 15 用作“谁都不碰”还是留给地面；脊柱插骨策略（新插 上半身1 还是 上半身3）；XNA Lara `spine lower` 映射到 上半身 还是 下半身；A-pose 角度（37° 还是 Convert_to_MMD5 的 36°）。

### 10.5 吸取 C2M 教训的架构约束
1b.6 的 12 条全部适用，其中最关键的五条：
1. 骨骼规格与映射只有一份 CSV，带 schema 版本，载入即校验；代码里不散落骨名字面量。
2. 映射状态存进 .blend（PropertyGroup / CollectionProperty）+ 外部 CSV，不用模块级全局变量。
3. 失败必须可见：操作符传播 CANCELLED 和异常，禁止静默回退与意外的文件副作用；检查器的期望值只来自规格表。
4. 纯 Python 核心配离线单测（mock 骨架），Blender 端用无头端到端测试；文档只写测过的东西。
5. 先在 1–2 个真实 XPS 模型上把一个阶段做到可验收，再做下一个；先移植已验证的算法（roe worker、Convert_to_MMD5、C2M 旧权重算法），不重写。

### 10.6 现有工具都没覆盖的缺口
1. **通用 XPS 输入**：owner 已跑通的流程起点都是游戏 FBX（ROE 的 Biped）或 UE 导出；对 XPS 只有 Convert_to_MMD5 的一份 `xna_lara.json` + 识别器。XPS 特有问题没人系统处理：`root ground` / `root hips` 的语义、`unused bip001 …` 辅助骨、XPS 的乳/臀/side 骨（pmxconv 的 `左breast`、`左side`）、foretwist、`spine middle` 去向分歧、导入后骨架轴向。
2. **CSV 映射表 + 检查器 UI**：没有现成实现。Convert_to_MMD5 是每预设一个 JSON；bones_renamer 的 CSV 只用于改名；xps_to_mmd 的 Check Bones 只打印到控制台。需要新做：CSV schema / 版本 / 校验、逐槽 `prop_search` 面板 + 状态图标、检查报告面板（可点击定位骨骼、高亮顶点）、“识别结果 / 预设 / 用户修改”三方差异视图。
3. **XPS 导入时采集高清材质 + PMX 导入后通用回挂**：三个现有插件都依赖游戏专用存档或游戏包解析，没有“从 XPS 自带贴图（颜色 / 法线 / 高光 / lightmap / 遮罩）回挂”的通用实现（第 4 节末给出了方案）。
4. **XPS 脸的表情**：所有角色表都不认 XPS 脸骨名（`head jaw`、`head eyelid …`、`head lip …`），也没有“每只眼一根眼睑骨”的配方；需要补 XPS 拼写、单眼睑骨配方（`move` 或顶点组掩码来源）、闭眼时眼球按侧后退、按网格角色分配；owner 清单里的 `激怒` 不在任何配方中；材质 morph（照れ）、瞳大、涙、组合 morph 都没有实现；非 ARKit 形态键（VRoid / DAZ / CC4）的别名表与“日文 MMD 名 → 分类”表也要新做（第 5 节）。
5. **物理分类的数据化**：身体 / 胸 / 衣物 / 头发目前靠正则 + 形状推断；应在 CSV（或单独的“物理链表”）里可查、可改，并纳入检查器（链长、锚骨、碰撞组）。
6. **mmd_tools 1.0.2 适配与回归**：02 号笔记基于 4.5.5；1.0.2 的操作符参数、属性定义方式不同，需要适配层和回归测试。
7. **XPS 验收集**：RT 已有 VMD 跳舞渲染（`scripts\riseoferos\render_pmx_dance.ps1`）和 `scripts\blender_mcp\vmd_check.py` 体检脚本（`RT/docs/roe-pmx-manual-guide.md` §3），但没有面向 XPS 的固定验收模型；建议用第 9 节的 Tifa 样例 + 2–3 个常见 XPS 模型建回归集。
